reCAPTCHA：出口を家に寄せ、漏れ道を塞いだあとの測定

2026-11-18 測定・鍵は fresh2（捨てアカウント）・各マス n=16（撃ち足していない）

結論：漏れ道（WebRTC の UDP・Chrome 自身の名前解決・音声の取得）を塞いでから、GCP の箱の出口を家の回線へ寄せた。その結果、即時通過は 13/16 から 6/16 に下がった。差は +0.44 で、95% 区間は [+0.10, +0.66]。区間が 0 をまたがないので、偶然の揺れでは説明しにくい。トークンは 16/16 で、課題を解けば全部通った。

「即時通過は出口の IP の評判だけで決まり、漏れ道は効いていない」という見立ては、この結果と合わない。

携帯回線（黒7a を出口にした段B）は壁だった。16 回すべてが SOCKS への接続で落ち、有効な試行は 0 回。原因はまだ診断していない。

1. 何を測ったか

Cloud Run の箱の Chrome から、公開している的（reCAPTCHA v2 のフォーム）を 16 回ずつ開いた。数えたのは次の 2 つ。

  • 即時通過：チェックを押しただけで課題が出ずに通った回の割合
  • トークン：課題を解いた回も含め、最後にトークンが出た回の割合

出口は tailnet の exit node で切り替えた。段A は PC を経由して家の回線（NTT PC・AS2514）から、段B は黒7a を経由してモバイル回線（Wi-Fi を切った状態・AS4686）から出した。どちらの段も撃つ前に門で確かめた。門は、箱から見た外向き IP の sha 先頭8桁が、PC または端末そのもので読んだ IP の sha と一致することを見る。段A・段B とも一致した。

5. 漏れの検査

撃つ前に1回、使い捨ての Chrome で 2 通り確かめた。1 つは腕と同じ旗の「塞いだ」側、もう 1 つは SOCKS だけの「塞がない」側。

項目段A（家）段B（携帯）
WebRTC（塞いだ側）候補 2 件・どちらも host の mDNS・漏れなし同じ（host の mDNS 2 件・漏れなし）
WebRTC（塞がない側）候補を読めない候補を読めない
名前解決の resolverどちらの側も読めず（答えの形が JSON でない・もう片方はエラー）どちらの側もエラーで読めず

塞いだ側では、外向きの候補（srflx・relay）が出なかった。塞がない側は候補そのものを読めなかったので、「塞がなかったら漏れていた」とはこの検査からは言えない。名前解決の resolver も両側で読めなかった。

6. 段B（携帯）の壁

  • 門は通った。箱から見た IP の sha が、Wi-Fi を切った黒7a そのもので読んだ IP の sha と一致した（AS4686）
  • 16 回すべてが Page.goto: net::ERR_SOCKS_CONNECTION_FAILED または 30 秒のタイムアウトで落ちた。有効な試行は 0 回
  • tailnet の経路は、直結でなく中継（DERP・東京）だった。Android の exit node は端末の中で包みを組み立て直す作りで、中継越しに Chrome の多数の接続を流したときに詰まった可能性がある。ただしまだ診断していない
  • モバイル通信の使用量は約 26MB で、上限の 100MB を下回った。撃ち足しはしていない

7. 元に戻したもの

  • PC：exit node の広告をやめ、承認も外した（routes は広告・承認とも空）
  • 黒7a：承認を外し、アプリの exit node を止め、Wi-Fi を入れた。端末の鍵も手放した。撃つ前から exit node を広告していた（承認はされていない）状態だったが、いまは止めてある
  • Job の env：撃つ前と同じ 2 本の名前のまま（実行ごとの上書きだけを使った）
  • Tailscale の API トークン：撃ち終えたあとに失効させ、そのあと API が 401 を返すことを確かめた
  • ACL：既存の許可を使っただけで、足しても消してもいない

8. 次の一手

  • 即時通過が塞いだあとに下がった理由を分ける。候補は、音声の取得を Chrome の網に寄せたこと（課題を解いた回の後の cookie）と、名前解決を SOCKS 側へ寄せたことの 2 つ。片方ずつ外して撃てば分かる
  • 段B の SOCKS の接続の失敗を診断する（直結の経路を取れるか・PC の網を通さない形）。直るまで携帯のマスは空のまま
