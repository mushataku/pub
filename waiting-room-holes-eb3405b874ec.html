続き：仮想待合室のしくみ（前編）

Queue-it を入れたら公平になるのか
――穴の地図と、自分でやること

0先に結論：これ、本当に使える？

✅ サイトを落とさない → 使える

何十万人が来ても、サイトに入るのは毎分◯人だけ。これは契約して設定すれば Queue-it が丸ごとやってくれる。

⚠️ 公平に売る → 自分次第

Queue-it が出すのは道具だけ。どれだけ公平になるかは、サイトへの組み込み方と自社の会員の仕組みで決まる。

穴は無数にあるわけではありません。根っこは2つで、そこから7つの穴が出ているだけです。7つのうち6つは最初に1回正しく作れば塞がる種類です。ずっと戦い続けるのは、穴1（アカウント量産）の1か所だけです。

1根っこは2つだけ

どちらも世の中で決まった呼び名がある、よく知られた問題です。「シビル攻撃」はブロックチェーンや口コミのサクラと同じ問題で、「持参人トークン（bearer token）」は Web のログイン全般で出てくる問題です。

物理で言うと、不公平は消えずに「一番偽造しやすい単位」に流れていきます。先着販売なら「速さ」に、抽選なら「並んだ数」に流れる。守る側がやることは、その単位をだんだん偽造しにくいものへ置き換えていくことです。

2穴の地図：お客さんの道のりのどこに穴があるか

お客さんがチケットを買うまでの道のりを左から右に並べ、穴の位置に番号を付けました。紫は根っこ1から、オレンジは根っこ2から出ている穴です。

紫＝根っこ1（1人が何人分にもなる）／オレンジ＝根っこ2（券や入口が誰でも通す）。

37つの穴と、自分がやること

穴ごとに、左に「何が起きるか」、右に「どう塞ぐか」を書きました。塞ぐ手には担当のラベルを付けています。

穴1アカウントを量産する根っこ1
何が起きるか

捨てメールで会員を何百個も作る。穴2をいくら塞いで「1会員＝1か所」にしても、会員が500個あれば500か所並べてしまう。

塞ぎ方
  • 会員の仕組み登録時に SMS 認証。1つの電話番号＝1会員
  • 会員の仕組み人気の販売は「購入実績がある会員」「◯日前までに登録した会員」だけに絞る
  • 会員の仕組み必要ならクレジットカードの名義や本人確認書類まで上げる

★ここが最後まで残る本当の勝負所です（4章）。

穴2タブを500個開いて何人分も並ぶ根っこ1
何が起きるか

待合室は「番号札の Cookie 1枚＝1人」と数えている。番号札を何枚も作られると、抽選のくじを何枚も引かれる。LINE の「タブ500個で抽選番号を見る」はこれ。

塞ぎ方
  • サイトの作り並ぶ前にログインさせる。待合室へは、会員IDを入れた入場トークン付きでしか入れないようにする
  • Queue-it の設定公式で確認済み会員IDごとに列は1か所（一意キーの強制）＋列に入るためのトークン必須

Queue-it の事例では、1本のリンクを31,000回開いた転売屋も、列には1か所しか取れなかったとのこと（Queue-it 自身の発表）。

穴3bot で機械的に大量に並ぶ根っこ1
何が起きるか

プログラムがデータセンターのサーバーから何千も同時にアクセスして並ぶ。

塞ぎ方
  • Queue-it の設定公式で確認済み列に入るところで計算の課題（proof of work）や CAPTCHA
  • Queue-it の設定公式で確認済みデータセンターの IP アドレスを拒否

これは「数を作る値段」を上げるだけで、ゼロにはなりません。穴2のログイン必須と組み合わせて、初めて並ぶ数そのものを絞れます。

穴4順番が来た URL を使い回す・人に配る根っこ2
何が起きるか

入場券は URL の末尾の文字列。署名と期限しか見ていないと、コピーした URL を開いた人は誰でも入れる。LINE の「抽選の先の URL を拾って買いまくる」はこれ。

塞ぎ方
  • Queue-it の設定公式で確認済み入場券の期限 ts を短くする。公式の部品は、入場が済むと URL から入場券を消す（共有防止のため）
  • Queue-it の設定公式で確認済み入場券に発行時の IPを入れて確かめる（一部の組み込み方式で対応）
  • サイトの作り公式に見当たらない使った券の列番号（q）を台帳に記録し、2回目は拒否する
  • サイトの作り入場時にログイン中の会員と、列に並んだ会員が同じかを照らし合わせる
穴5待合室を素通りして直接入る根っこ2
何が起きるか

入場の確認が、ブラウザに読み込ませる JavaScript だけだと、それを動かさない道具で直接サイトを叩けば通れてしまう。確認係が「お客さんの手の中」にいる状態。

塞ぎ方
  • サイトの作り公式で確認済み確認はサーバー側か CDN の手前（エッジ）でやる。Queue-it は各言語・各 CDN 向けにこの部品を出している
  • サイトの作りブラウザ側の確認は、表示を整えるためのおまけと割り切る
穴6守っていない裏口（API）から注文する根っこ2
何が起きるか

商品ページは待合室で守っているのに、「カートに入れる」「注文する」の裏の窓口は守っていない。正面玄関は行列なのに、裏口が開いている状態。

塞ぎ方
  • Queue-it の設定守るURLの規則は「全部守る」から始めて、外すものだけを書く
  • サイトの作りカート・決済の API でも、入場 Cookie（なければ入場済みの記録）を必ず確かめる
穴7一度入ったら買い放題根っこ2
何が起きるか

入場 Cookie の寿命（ポケセンなら約20分）の間、何回でも注文できる。抽選で1回当たれば、それで在庫を持っていける。

塞ぎ方
  • サイトの作り入場1回＝注文1回。注文が終わったら入場 Cookie を捨てて、次はまた並ばせる
  • サイトの作り会員ごとの購入上限を、注文の段で機械的に止める（画面の案内だけにしない）
  • Queue-it の設定入場 Cookie の寿命を、1回買うのに足りる長さまで短くする

4やる順番

塞げる範囲が広くて手間が小さいものから並べました。上の5つは「1回作れば終わり」、最後の1つだけが「ずっと続く勝負」です。

  1. 確認係をサーバー側（エッジ）に置き、全URLを守る　サイトの作りQueue-it の設定
    穴5・穴6。ここが開いていると、他を全部塞いでも横から入られる。土台。
  2. 並ぶ前にログイン＋会員IDごとに列は1か所　サイトの作りQueue-it の設定
    穴2。「タブ500個」が一発で無意味になる。抽選にするならこれは必須。
  3. 入場1回＝注文1回、会員ごとの購入上限　サイトの作り
    穴7。当たった1人の買い占めを止める。
  4. 入場券の台帳＋会員の照らし合わせ＋短い期限　サイトの作りQueue-it の設定
    穴4。URL を拾って使い回す手がなくなる。
  5. bot 対策（計算の課題・CAPTCHA・データセンターIPの拒否）をオン　Queue-it の設定
    穴3。設定だけでできる。
  6. 会員1つを作る値段を上げる（SMS 認証、購入実績のある会員に絞る、本人確認）　会員の仕組み
    穴1。ここだけは終わりがない。電話番号を大量に用意する業者もいるので、商品の人気（転売で儲かる額）に合わせて、どこまで上げるかを決め続ける。

5それでも残るもの

  • 本物の人間が大勢で並ぶ（転売のために人を集める）。1人1会員を守っていても防げない。ここから先は「買った後」の話で、チケットの名義を固定する、入場時に本人確認する、公式のリセール（定価での譲渡）を用意する、といった待合室の外の手になる。
  • 電話番号を大量に持つ業者。SMS 認証は値段を上げるだけで、ゼロにはしない。だから「どこまで値段を上げるか」は、転売の儲けとの見合いで決め続けることになる。

6このページの確かさ

公式で確認済みのラベルは、Queue-it の公式サイトと公開されている組み込み部品の説明に、機能として書かれているものです。実際に契約して動かしたわけではありません。数字（31,000回など）は Queue-it 自身の発表です。

公式に見当たらない入場券を1回しか使えなくする機能は、公式の説明では見つかりませんでした。見落としの可能性もあるので、契約するなら営業担当に「使った入場券を2回目に拒否できるか」を直接聞くのが確実です。

ローチケやポケセンなど、実際のサイトがどこまで塞いでいるかは調べていません。
