1. 一枚目のまとめ

  1. Playwright で普通に起こした Chrome は、チェックボックスを押しても即時には一度も通らない。原因は 2 つで、Playwright が画面の大きさを上書きすることと、Chrome をパイプで起こすこと。
  2. パイプで起こすと navigator.webdriver が true になる。この旗 1 つを消すと、パイプのままでも普通の Chrome と同じ率で通る（Ppw 31/64・同じ回の C 27/64）。
  3. headless は画面と UA の両方に跡が残る。片方だけ直しても 0 のまま、両方直すと普通の Chrome と同じ率（Hsu 27/64・C 27/64）。11-16 に 4 つの組を同じ回に並べても同じだった（画面だけ 0/16・UA だけ 0/16・両方 10/16・C 13/16）。
  4. 普通の Chrome（C）でも、同じ回線から撃ち続けると即時の通過が 0 近くまで落ち、何時間か休むと戻る（はしご⑤ 13/15 → 翌朝 0/15、C 0/16 → 休んで 15/16）。即時に通らなくても、音声の問題を解けば最後はほぼ取れる（C は 48/48）。

つまり reCAPTCHA は、少なくとも「webdriver の旗」「headless の画面と UA」「Playwright の画面の上書き」の 3 つを、押した瞬間に bot と決める印として使っている。3 つを全部消した bot は、同じ回線・同じ時間帯では普通の Chrome と率が変わらなかった。

2. 言葉の整理

即時の通過／最終的に取れた
チェックボックスを押してから 8 秒以内に、画像や音声の問題なしでトークン（合格証）が出たら「即時の通過」。問題が出ても、音声の問題を解き手（音声認識）に解かせてトークンが出たら「最終的に取れた」に数える。この研究の物差しは主に前者。 例え: 改札にカードをかざしてそのまま通れたのが即時の通過。止められて窓口で説明して通してもらえたのが、最終的に取れた。
パイプ（--remote-debugging-pipe）と TCP の口
プログラムから Chrome を動かすには、DevTools の命令（CDP）を Chrome に送る通り道が要る。通り道は 2 種類ある。TCP の口（--remote-debugging-port）は、Chrome がパソコンの中に受付の番号を開き、外から誰でもそこへ繋ぎにくる形。パイプは、Chrome を起こした親のプログラムだけが持つ専用の管で繋ぐ形。Playwright の launch はパイプで起こす。 例え: TCP の口は店の代表電話（後から誰でもかけられる）、パイプは起こした人だけが持つ直通の内線。
navigator.webdriver（webdriver の旗）
ページの JavaScript から読める true／false の値。W3C の WebDriver の決まりで「ブラウザが遠隔操作されているときは true」と定められている。Chrome は自動化用の起こし方のときにこれを true にする。今回の測定では、パイプで起こすと true になり、TCP の口だけだと false だった。--disable-blink-features=AutomationControlled という引数 1 つで false に戻せる。 例え: 車の「仮免許練習中」の札。中で誰が運転しているかに関係なく、札が付いていれば外から分かる。
headless（画面なしの Chrome）と、2 つの跡
窓を出さずに動く Chrome。今回はページの中から見える違いが 2 つあった。①画面の跡: 画面の大きさが 800×600・拡大率 1 になる（この PC の普通の Chrome は 1536×864・拡大率 1.25）。②UA の跡: ブラウザが名乗る名前（User-Agent）が「HeadlessChrome/156」になる（普通は「Chrome/156」）。 例え: 制服（UA）と背丈（画面）の 2 つで見分けられている人。制服だけ着替えても背丈で、背丈だけ合わせても制服で見分けられる。
画面の上書き（Playwright の viewport）
Playwright は既定で、ページの中から見える画面を 1280×720・拡大率 1 に固定する（Emulation.setDeviceMetricsOverride という命令）。実際のモニターとは食い違う値になる。
C（対照）
自前の起動処理で chrome.exe を普通に起こし、TCP の口から Playwright で繋いだ Chrome。押し方は他の組と同じ。毎回の束に必ず混ぜ、その回の基準にした。
cohort・鍵・ミラー
cohort は、新しく作ったブラウザのプロファイル（cookie や履歴の入れ物）1 つ。8 回撃つごとに新しくした。鍵は reCAPTCHA のサイトキーで、Google のアカウントで発行する本物を 2 本使った（末尾 tYwR と wYph）。ミラーは、手元のパソコンで動かす自前の申込フォームで、そこに本物の reCAPTCHA を載せた。判定は Google の本物のサーバが行う。 例え: 自分の店の入口に、警備会社の本物のゲートを付けて、自分で何度も通ってみた。

3. 測り方

  • 的: 手元の自前ミラー（localhost）に、本物の reCAPTCHA v2 チェックボックスを載せた。鍵は 2 本（2026-09 発行の 1 本目・末尾 tYwR と、11-15 に別のアカウントで発行した 2 本目・末尾 wYph）。11-15 の昼からは 2 本を別々のミラーで同時に撃った。
  • 回線: 家の回線（プロキシなし）。ブラウザは普通に配られている Chrome（版 156）。押すのは素の el.click() で、マウスは動かさない。
  • 束: 8 回ごとに新しい cohort を作る。束の中では回ごとに組の順番を入れ替え、組どうしで時間帯がずれないようにした。
  • C を毎回まぜる: 回線の状態で率が大きく動くので、どの束にも C を入れ、比べるのは同じ回の Cとだけ。
  • 検定: Fisher の正確検定（両側）。0 と 40% くらいの差なら 1 組 16 回で p≈0.02 に届く。
  • 先に偽物で確かめる: 本物を撃つ前に、Google に行かない偽の reCAPTCHA で、ページの中から見える値（画面・UA・webdriver・プラグインの数）を組ごとに読んだ。組の違いが狙いどおり 1 つだけかをここで確かめた。
  • 止める条件: ①鍵の無料枠（フォームは送らないので siteverify は 0 回） ②C の疲れ（直近の C が 16 回中 4 回未満になったら止める。その時間帯は組を見分けられない）。
  • 撃った回数: 11-14〜11-15 に本物の reCAPTCHA へ撃った試行は約 1,400 回（図に入れたのはそのうちの各回の比べる束）。

4. 分かったこと

どの図も、横の棒が即時の通過の率、細い帯が ±1 標準誤差、点線がその回の C の率。右の数字は回数と、同じ回の C との p。0 の組は数字を赤くした。図ごとに撃った時間帯が違うので、図をまたいで率を比べないでほしい。

4.1 Playwright の起動には、0 を作る原因が 2 つある

11-14 の夜、Playwright の launch で起こした組は 0、自前で起こして後から繋いだ組は C と同じ率、という差がまず出た（図 1a）。動かす道具を patchright に替えても変わらないので、差は「起こし方」の側にある。そこから束を 1 つずつ割った。

まとめると、launch がしていることのうち、画面の上書き（図 1c の I）とパイプで起こすこと（図 1c の P、図 1e の N）がそれぞれ単独で即時の通過を 0 にする。起動の旗 37 個、プロファイルの形式、親プロセス、窓の大きさの上書き、自前の手か Playwright の手か、はどれも率を変えなかった。

4.2 パイプの 0 は、webdriver の旗 1 つで説明できる

パイプのどこが問題かを割った。パイプを開くだけで命令は TCP の口から送る組（Ppp）でも 0 だったので、命令がパイプを通ることは関係ない。偽物で読むと、Ppp と C の違いは navigator.webdriver が true になることだけだった。そこで Ppp にこの旗を消す引数を 1 つ足した（Ppw）。

4.3 headless の 0 は、画面と UA の両方を戻すと消える

headless は、起こし方を C と同じにしても 0 だった（図 3a）。画面だけ、UA だけを C に寄せても 0 のまま（図 3b）。両方を同時に戻した Hsu は C と同じ率になった（図 3c）。なお Hsu の内寸の高さは 702 で、C の 703 と 1 px だけ違うが、率は変わらなかった。

図 3b と図 3c は撃った時間帯が違う（11-15 昼の C は 11/48、夕の C は 27/64）。そこで 11-16 の昼に、C・Hsu・Hs・Hu の 4 つの組を同じ回に順番を入れ替えて並べた（図 3e）。回線を 5 時間以上休ませた後で、直前の確かめでは C が 16/16 通った。

同じ回の中で C と比べると、C が通って Hs が通らなかった回は 16 回中 13 回、その逆は 0 回だった（Hu も同じ 13 対 0・McNemar p<0.001）。Hsu は 4 対 1（p=0.375）。鍵 2 本とも同じ向きだった（CtYwR: C 8/8・Hsu 5/8・Hs 0/8・Hu 0/8、1wYph: C 5/8・Hsu 5/8・Hs 0/8・Hu 0/8）。1 つの組あたり 16 回で決着したので、それ以上は撃っていない。headless の 0 を消すには、画面と UA の両方を直す必要がある。

4.4 回線の疲れ: 同じ回線から撃ち続けると C も落ち、休むと戻る

C の即時の通過を、撃った時刻の順に並べた。束ごとの点で、上下の線は ±1 標準誤差。

新しい回線の状態で即時の通過が読めるのは、1 本の鍵あたり 50〜60 回くらいまでだった。2 本の鍵で同じ速さで落ちたので、疲れているのは鍵ではなく家の出口の IP（回線）の評判と読むのが自然。どれくらい休めば戻るかは、2 時間で足りない日もあった。

4.5 即時に通らなくても、最後はほぼ取れる

即時の通過が 0 の組でも、音声の問題を解けば多くが取れた。例外は旧 headless（Ho）で、音声の段まで含めて 0/48 だった。

5. 自分のサイトで bot を見分けるときの意味

reCAPTCHA に任せてよいこと

  • webdriver の旗・headless の UA と画面・Playwright の画面の上書きの 3 つは、reCAPTCHA が押した瞬間に問題を出す。道具をそのまま使う素朴な bot には、毎回問題を解く手間がかかる。
  • 同じ回線から大量に撃つ bot は、回線の評判が落ちて C 並みのブラウザでも問題が出るようになる。

reCAPTCHA だけでは足りないこと

  • 音声の問題は機械で解ける。即時に通らなかった bot も、最終的には 9 割前後が通った。reCAPTCHA は「止める」ではなく「手間を足す」道具と見る。
  • 3 つの跡を消した bot は、同じ回線では普通の Chrome と率が変わらない（Hsu・Ppw ＝ C）。跡の消し方は公開の道具に入っている（6 章）。

自前で見る軸（docs/detection-catalog.md の項目）

  • 辻褄: UA と Client Hints、画面と窓の大きさ、言語とタイムゾーンが食い違っていないか（Hsu の内寸 702 対 703 のような小さなずれも、組み合わせると手がかりになる）。
  • CDP の跡: Runtime.enable などの命令の副作用。ただしこの手の印は Chrome の更新で消えることがある（6 章の Castle の記事）。
  • 操作のしかた: 今回の bot は素の el.click() でマウスを一切動かしていない。マウスの軌跡・入力の間隔・押すまでの時間は自前で記録できる。
  • 頻度と流れ: 同じ回線・同じ人からの回数、ページを開いてから送るまでの時間、音声の問題を選んだ回の多さ。reCAPTCHA の「回線の疲れ」と同じものを自前で数える。

6. 世の中でどこまで知られているか

論文・道具・仕様・掲示板を調べた結果を、「個々の事実が知られているか」と「今回の形の対照実験が公開されているか」に分けて書く。

個々の事実は、ほとんど知られている

webdriver が自動化の印になること: W3C WebDriver の仕様が「遠隔操作中は true」と定める。headless 検知を避ける道具 puppeteer-extra-plugin-stealth は、この旗を消す処理を個別に持つ（起動に --disable-blink-features=AutomationControlled を足す）。Playwright を改造した patchright も同じ引数を足し、--enable-automation を外す。
ただし Sivakorn ら（IEEE EuroS&P 2016）は、webdriver を true にしてもチェックボックスの判定は変わらなかったと報告している。今回は 0 になった。10 年の間に Google が見るようになったのか、パイプで起きた Chrome に別の跡もあるのかは、この測定では分けていない。

https://www.w3.org/TR/webdriver2/ ／ https://github.com/berstend/puppeteer-extra/tree/master/packages/puppeteer-extra-plugin-stealth/evasions ／ https://github.com/Kaliiiiiiiiii-Vinyzu/patchright

headless の UA と画面が跡になること: stealth の道具は UA の「HeadlessChrome」を「Chrome」に置き換える処理と、headless で欠ける窓の外寸を補う処理を別々に持つ。Venugopalan ら「FP-Inconsistent」（2024）は、bot の指紋の属性どうしの食い違い（実在の端末にない組み合わせ）で検知できることを示した。Sivakorn ら（2016）は、UA が実際のエンジンと食い違うと問題が出ること、画面の大きさを 1×1 から 4096×2160 まで変えても判定は変わらないことを報告している。headless そのものは測っていない。

https://arxiv.org/abs/2406.07647 ／ stealth の user-agent-override・window.outerdimensions（上の evasions の中）

IP・cookie・履歴で判定が変わること: Sivakorn ら（2016）は、9 日寝かせた cookie でチェックボックスだけで通ること、Google の新しいアカウントは悪い評判から始まること、頻度が高いとブロックされることを示した。Plesner ら「Breaking reCAPTCHAv2」（COMPSAC 2024）は、VPN で IP を替えないと 19 回目あたりから問題が増え、cookie と履歴があると必要な問題の数が減ると報告し、reCAPTCHA v2 は "heavily based on cookie and browser history data" と書く。Google の公式 FAQ も、IP の評判と cookie をリスク分析に使うとだけ書いている。

https://arxiv.org/abs/2409.08831 ／ https://developers.google.com/recaptcha/docs/faq

音声で破れること: Bock ら unCaptcha（USENIX WOOT 2017）が音声の問題を 85.15% で解いた。同じ論文に、Mac の Selenium は検知され、ChromeDriver が残す変数名を書き換えると避けられた、という観察もある。

https://www.usenix.org/conference/woot17/workshop-program/presentation/bock

Playwright が画面を上書きすること: 公式の API 文書に「既定で 1280×720 の固定の viewport」とある（no_viewport で外せる）。CDP を使っていること自体を検知する手（Runtime.enable の副作用）は DataDome・Castle が書いているが、Castle は 2025 年 5 月の V8 の変更でこの印が使えなくなったと報告している。

https://playwright.dev/python/docs/api/class-browser#browser-new-context ／ https://blog.castle.io/why-a-classic-cdp-bot-detection-signal-suddenly-stopped-working-and-nobody-noticed/

今回の形の対照実験は、見つからなかった

「起こし方の違いを 1 つずつ戻し、毎回 C と同時に撃ち、即時の通過の数を検定で比べる」形で reCAPTCHA v2 を測った公開物は、調べた範囲では見つからなかった。近いのは次の 3 つ。

  • Sivakorn ら（2016）は 1 変数ずつ変える設計だが、測ったのは webdriver・画面・UA・cookie などで、パイプ・headless・Playwright の画面の上書きは無い。結果も今回と食い違う（webdriver・画面は 2016 年には影響なし）。
  • Plesner ら（2024）は VPN・マウス・cookie を足し上げて比べたが、物差しは解くまでの問題の数で、ブラウザの起こし方は測っていない。
  • 道具の README やベンダーのブログに「素の Playwright は問題が出る」「patchright の headless は v3 で通らない」といった単発の記述はあるが、回数と対照は無い。

回線の疲れ（同じ回線の C が 13/15 から 0/15 に落ち、休むと戻る）を時刻つきで測った公開物も見つからなかった。

調べた先: arXiv・USENIX・NDSS・ESORICS・IEEE の論文、Google の公式文書、GitHub（stealth・undetected-chromedriver・patchright・rebrowser-patches）、Stack Overflow、Reddit（r/webscraping）、DEV Community、ベンダーのブログ（DataDome・Castle・capsolver）、Zenn・Qiita・note、Hacker News、BlackHatWorld。Hacker News と BlackHatWorld は検索から本文に届かなかった。検索は英語が中心で、日本語の当事者の記録はほぼ空振り。「誰もやっていない」とは言えない。

「ここまで解明している人は世の中にいるか」への答え: 個々の跡は道具の作り手が知っていて、とっくに消し方まで配られている。ただ、それぞれの跡が reCAPTCHA の判定をどれだけ動かすかを、対照を置いて数で示したものは見当たらなかった。しかも 2016 年の論文とは webdriver と画面で結論が逆になっている。

7. まだ分かっていないこと

  • 3 つ以外の跡: 今回消したのは webdriver・UA・画面だけ。マウスの動き、Client Hints、CDP の副作用などを reCAPTCHA が見ているかは測っていない（今回の bot はマウスを動かしていないのに、C は通った）。
  • headless は本当に AND か: 11-16 に同じ回に並べて確かめた（図 3e）。画面だけ・UA だけでは 0/16 のままで、両方を直す必要がある。残っているのは、Hsu（10/16）が C（13/16）より少し低い差が本物かどうか（p=0.433・16 回では分けられない）。
  • 評判の中身: 回線の疲れが IP だけで決まるのか、何回・何時間で落ちて何時間で戻るのか。2 時間で戻らない日があった。
  • パイプの 0 は webdriver だけか: 2016 年には webdriver で判定が変わらなかった。今回は Ppw で戻ったので webdriver が引き金なのは確かだが、Google がいつから見ているのかは分からない。
    11-16 に起動の旗を 1 本ずつ足し引きして、webdriver が立つ分岐を絞った（偽の reCAPTCHA で navigator.webdriver だけを読み、Google には撃っていない）。--remote-debugging-pipe だけで true（--enable-automation は無し）、--enable-automation だけでも true（パイプ無し）。どちらも --disable-blink-features=AutomationControlled を足すと false。つまり webdriver を立てているのは、パイプでも --enable-automation でもなく、どちらからも立つ Blink の AutomationControlled の方だった。本番で C と並べた 16 回は、即時通過が C 6/16・Ppw 7/15（p=0.72）で、最終的に取れた数は 16/16 と 15/15。差は出なかった。
  • 日々の変化: OS のカーソルで押す組（real_os）と、cookie を寝かせる日次の測定は 11-16 以降に結果が出る。
