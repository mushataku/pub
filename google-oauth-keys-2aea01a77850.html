Google アカウントの鍵の持ち方：決めたことと、武者野さんの手

武者野さん向けの報告（社内の設計報告）。設計の決着：2026-11-03。この資料の数字は特記がなければ 2026-11-03 時点の棚卸しです。

§0一言：何が決まったか

アカウントごとに主鍵を 1本。クライアント（Google に登録する名札）は共通の 1つ。開発環境で鍵を使う入り口は、こちらで作る道具 gkeys（ジーキーズ）の 1つ（本番の読み方は変えず、鍵だけ新しい版に入れ替える）。

本番が自分で更新し続けている鍵などは動かさず、名指しの例外として台帳（名簿）に載せます（§2 決定1）。持ち主の分からない鍵は、消すか、持ち主を根拠つきで記録して残します。図で見たいときは §3 の前後比較図 へ。

手：27〜45 押し（要実測）

Google の許可画面を 9アカウント分、1アカウントあたり 3〜5回押す想定です。実際の画面を誰もまだ見ていないため、最初の mushik で実測して回数を確定します。詳しくは §5。

費用：増やさない設計

新しい契約も新しいクライアントも作りません。片付けの 14日後に、鍵の保管数が着手前以下かを数えて確かめます。詳しくは §6。

止まるもの：なし

本番を止める段はありません。切り替えは道具 1つずつで、戻し方を 1行つけて進めます。

1-3何が困るか（右端の「→」が対応する決定）

  • 持ち主の分からない鍵がある。消してよいか誰も確かめられません。→ 決定 1・5
  • 同じアカウントに鍵が何本もある。許可の範囲も置き場もばらばらで、どの道具がどれを読むかは棚卸しをしないと分かりません。→ 決定 1・3・4

§2決めたこと

鍵に関する決定が 1〜7、費用と安全に関する決定が 8〜10 です（8〜10 は §6）。各カードは「前 → 後」で読めます。

1鍵の単位：アカウントごとに主鍵 1本

前道具ごと・事業ごとに別の鍵が散らばっていた。
後共通の名札で取った鍵 1本を、全道具が読む。例外は台帳の行で名指しする（範囲を狭めて分けた鍵・本番が自分で更新し続けている鍵・管理設定で共通の名札が弾かれるアカウント）。

2名札（クライアント）：共通の 1つ

前名札が 4つ（個人側に 2つ・会社・bot-lab の事業）。
後Gmail の道具が 5アカウントで既に共用している個人の名札を共通にし、表示名を「Mushano Tools」に改める（同意画面にもこの名前で出る）。新しい名札は作らない。ドライブ・スプレッドシート・ドキュメント・カレンダー・連絡先・タスクの API を有効にする（無料・戻せる）。
補足名札は課金も権限も持ちません。事業の境目は名札では引かず、鍵の置き場（その事業の保管庫）と台帳の事業の列で引きます。この名札は公開の設定が済んでいる見込みです（A で機械的に確かめます）。Google の審査は受けていないため、同意画面に「未確認」の警告が出ます（§5-1）。

3許可の範囲：全部入りの一式を最初から取る

前鍵ごとに許可の範囲がばらばら。
後Gmail 全部・ドライブ・スプレッドシート・ドキュメント・カレンダー・連絡先・タスクの一式。デスクトップ型（PC 用）の名札は、後から範囲だけを足す追加の同意ができないためです。足すときは一式に 1行足して、押し直します（手が要ります）。Gmail の細かい許可（読むだけ・送るだけ等）も一式に入れます。道具が「読むだけ」という名前で許可を求めるとき、その名前が一式に無いと Google が拒むためです。

4置き場と書き手：鍵を書くのは同意のときだけ

前鍵の書き手も置き場も道具ごと。
後書き手は gkeys consent だけ。PC の決まった場所に保存し、運搬の箱で VM へ届ける。本番が使うアカウントは、その事業の保管庫の既存の名前に「同名の新版」として入れる。名前を変えないので設定の更新が要らず、戻すときは新版を無効にして、本番は同じ手で起動し直す。鍵の中身は道具がいま読む形式のままで、「どのアカウントか」「実際に許可された範囲」「取った日時」を添える。

5口と台帳：開発環境の入り口は gkeys 1つ

前道具が各自のやり方で鍵のファイルを読んでいた。名簿も複数あった。
後開発環境の道具は「このアカウントのこの範囲の一時パスをください」と gkeys に頼む。名簿（台帳）は 1枚で、アカウント・事業・置き場・例外の鍵が載る。gkeys は全 repo 共通の道具置き場に置く。claude-ops には置かない（他の事業の VM から見えないため）。本番（Cloud Run）は gkeys を使わず、いまのコードのまま鍵を読む。

6同意の手：画面は道具が開き、押すのは武者野さん

前鍵ごとに別々に同意を取り直す必要があった。
後道具がそのアカウントの Chrome プロファイルで同意画面を前面に開く。自動では押さない。武者野さんの手は 1アカウントあたり 3〜5押しの想定（§5）。運搬は押した直後に始まり、VM 側は次にセッションを開いたときから新しい鍵を使える。

7知らせ：切れたら直し方つきで知らせ、毎日確かめる

後鍵が切れたときは「何をすれば直るか」つきで知らせ、PC に任せられる作業は自動で票にする。保険として毎日 1回、PC の夜間の定期処理の直後に、全鍵を実際に更新して生死を確かめる。これは Google の 6か月失効も防ぎ、PC が数日止まっても失効しない。なお、武者野さんがそのアカウントの Google パスワードを変えると、主鍵は失効して同意（3〜5押し）をやり直しになります。知らせるのは失敗したときだけで、最終確認の時刻は Claude のセッションを開いたときの冒頭 1行に出る。

§4世の中の定番との対応

この設計は、世の中で「トークン保管庫（token vault）」と呼ばれる型を、個人規模に縮めたものです。接続ごとに許可証を 1か所へ保管し、使う側には短命の一時パスだけを渡し、切れたら検知して取り直す、という考え方です。

定番の手法と、この設計での扱い
定番ひとことでこの設計での扱い
トークン保管庫接続ごとの許可証を 1か所で持ち、使う側へは一時パスだけ渡す。切れたら検知して取り直す。採る gkeys と台帳がこれに当たる。
追加同意後から許可の範囲だけを足してもらう仕組み。使えない デスクトップ型の名札は非対応。一式を最初から取る（決定3）。
ドメイン全体委任（DWD）組織の特権管理者が、自ドメインの全員分を代理で許可する仕組み。届かない 自ドメイン限定で、個人の Gmail と alumni には適用できない。
公開手続き（未確認アプリ）アプリを Google が確認する前でも、個人利用 100人未満なら画面のクリックで通れる。通れる ホームページとプライバシーポリシーは github.io で満たせる。「未確認のままでは使えない」と書いていた以前の記録は誤りでした。

§6費用と安全（決定 8〜10）

武者野さんが気にする 2点、「お金は増えないか」「事故は起きないか」への答えです。

8費用の約束

不変条件：片付けの完了から 14日後に、請求アカウント別の「有効＋無効の保管版の数」が着手前以下であること（無効の版も課金される可能性があるので両方数えます）。着手前の数は gkeys plan が最初に記録します。個人側は、運搬の箱が容量超えで 2つになっても、着手前 +1 版まで（無料枠の中）です。
  • いまの保管庫の費用は、月およそ 2,200円です（bot-lab 約 1,989円・会社 約 189円・個人 0円。有効な版だけ数えた 2026-11-03 時点の実質額）。この設計はこれを増やしません。減らす作業は別の票（bot-lab の保管庫の掃除）です。
  • 新しいクライアントは作りません。API の有効化は無料で、戻せます。
  • 保管名は変えず、同名の新版を足します。足した分は、片付けで旧版を退避してから消して相殺します。

9安全の約束

  • 全部入りの主鍵は、混在した場所に読ませない。多くの job（クラウド側のプログラム）が共有する実行用の身分や、ブラウザ操作の job には主鍵を読ませません。gkeys plan がこの組み合わせを見つけたら赤で知らせます。
  • 正本を書くのは同意のときだけ。日々使う一時パスは別の置き場に置き、鍵のファイルは使っても書き換わりません（試験で確かめる）。
  • 本番は、鍵を足したあと一度起動し直す。本番は起動時にしか新しい鍵を読まないためです。新旧を並べて入れ替えるので止まりません。戻すときは新版を無効にして、同じ手で起動し直します。
  • 鍵の値は、この資料にもチャットにも出さない。同意の直後に本人確認（どのアカウントの鍵か）を検算して保存します。
  • PC が壊れても戻せる。主鍵の正本は PC にありますが、運搬の箱に写しがあります。新しい PC では運搬の箱から取り出します（C4）。
  • 単一障害点：共通の名札は個人側の Google Cloud プロジェクトにあります。この名札を削除すると主鍵 9本が全部失効し、名札を作り直して B の段をやり直し、expense-web の版を入れ直すことになります（削除はしないと決めています＝決定 10）。recruit 本番は据え置きなので影響を受けません。expense-web は主鍵に載せ替えるので影響を受けます。

10やらないこと（理由つき）

この計画で意図的に触らないもの
やらないこと理由
鍵の一括無効化（revoke）同じ Google Cloud プロジェクトの全クライアントの許可を巻き込んで失効させるため。
許可（grant）の取り消し・クライアント削除戻せない。片付けは鍵のファイルと保管版だけで行う。
会社のプロジェクトの同意画面・ブランドの変更組織内限定にすると、会社組織の外の Gmail である seed と shin が使えなくなる。
recruit 本番の鍵と週ごとの受信監視の移設本番が自分で更新し続けている。例外として台帳で名指しするだけ。
bot-lab の範囲を狭めた 4本の差し替え98 の job が使う信頼の低い殻で、全部入りの主鍵を渡さない方が安全。
ドメイン全体委任・名札のあるプロジェクトの第 2 の管理者（owner）個人の Gmail に届かない。管理者を増やすと権限の持ち主が見えにくくなる。
