CA向け・社内学習資料 ／ 入門編

CAのためのIT職種入門
「インフラって結局なに？」

IT求職者に語れるようになるための、最低限の地図。専門用語は出てきますが、全部その場か巻末で説明します。

📚 この資料は2本セットです

  • ① 入門編 この資料（約10分）— IT職種の名前と用語を知る。IT求職者を担当する人向け
  • ② 応用編 手順化度の軸（約15分）— 分野を問わず使える1本の目盛り。全CA向け

順番は①→②。②はこの資料の「インフラ3層（2章）」を全職種に広げた話なので、2章を読んでから②に行くと繋がります。

🗺️1. まず全体像 — 開発とインフラの違い

動くものを作る＝開発。動かし続ける土台を作って守る＝インフラ。

飲食店にたとえると、料理を作るのが開発、店舗・厨房設備・電気ガス水道を用意して止めないのがインフラ。どちらが偉いという話ではなく、担当が違います。

■ この資料に出てくる4つの言葉（これだけ先に）
  • サーバー = サービスを動かしている「店の厨房にあたるコンピュータ」。会社の中に置く場合と、他社から借りる場合がある
  • コード = 人がコンピュータに出す指示を、決まった書き方で書いた文章。「コードを書く＝手順を文章にして機械にやらせる」
  • DB（データベース） = 会員情報や注文履歴を貯めておく箱
  • クラウド = サーバーを自前で買わず、必要な分だけ借りる方式（AWS・Google Cloud 等）

これ以外の略語は7章の用語辞典にまとめてあります。読みながら分からない略語が出たら7章へ。

やること職種
アプリの機能を作る・画面を作る開発
サーバーを用意する・設定するインフラ
サービスが落ちてないか見張るインフラ
作ったものが仕様どおり動くか確かめるQA・テスト

🪜2. 最重要 — インフラは「3層」に分かれる

ここが一番大事。同じ「インフラエンジニア」でも、層が違うと中身も年収も将来性も別物。
求職者が「インフラで進みたい」と言ったとき、どの層を想像しているか必ず確認する。
第3層 ／ 到達点
設計・SRE
「このサービスは月1000万アクセスに耐える必要がある。だからこういう構成にする」と決める層。判断の仕事。年収1000万超も珍しくない。ただし入口ではなく、たどり着く場所。
▲ 1〜3年で上がるのが標準ルート
第2層 ／ 中堅
構築
「新しいサーバーを立てて、こう設定して」の指示を受けて実際に作る層。手を動かす仕事。
▲ ここを上がれるかが分かれ道
第1層 ／ 入口
運用監視（オペレーター・NOC）
アラートを見て、手順書どおりに対応する層。「CPUが90%超えたらこの手順、ダメなら上に報告」がマニュアル化されている。夜勤シフトがあるのはここ。未経験で入れるのもほぼここ。

🪙3. なぜ「未経験はインフラから」なのか

親切だから入口が広いのではない。手順化されているから広い。

第1層の仕事は手順書になっているので、未経験でも初日から戦力になります。
逆に開発は「未経験に何をさせればいいか分からない」——コードを書かせても先輩がレビューする時間の方が高くつく。だから育成コストを払える会社しか未経験開発を採らない。

これが、当社が扱うIT系求人のうち未経験可の枠がインフラに偏っている構造的な理由です。

（同じ「未経験枠が広い」でも、分野によって理由は違います。施工管理や介護で未経験枠が多いのは手順化されているからではなく人手不足が主因で、教え方も手順書でなく先輩について覚える形。だからこの後の「＝自動化されやすい」の話は、IT分野の構造として読んでください。）

↓ そして、ここが求職者に伝えるべき本質 ↓
😊 手順化されている＝未経験でも入れる。マニュアルがあるから初日から働ける。
😰 手順化されている＝AI・RPAで自動化しやすい。置き換えの第一候補になる。
「未経験でも入れる」と「自動化されやすい」は同じコインの裏表。
だから「インフラなら安泰」ではなく、「入口で止まらず、2層・3層へ上がれるか」が本当の論点。求職者にはここまでセットで伝える。

💧4. 開発とインフラの境界は溶けている

昔のインフラ＝データセンターに行き、サーバーの箱をラックに固定し、ケーブルを挿す。物理作業。

今のインフラ＝「サーバー2台、DBはこれ、ネットワークはこう」をコードで書くと、その通りにクラウドが作ってくれる。

つまり、現代のインフラエンジニアもコードを書く。

「開発＝コードを書く／インフラ＝書かない」という理解は、もう古い。求職者がこの前提で悩んでいたら、そこを解いてあげるだけで視界が変わります。

🔍5. QA・テストという第3の職種

作られたシステムが仕様どおり動くか確かめる仕事。

昔は人海戦術。「この画面でこのボタンを押して、この表示が出るか」を1項目ずつ人が手で確認していました。

今はテストをプログラムに書かせて自動実行させるのが主流。それを専門にやるのが SET／SDET という職種です。

SETはコードを書く仕事。テストコードを書き、自動実行の仕組みを作り、テスト基盤そのものを設計する。
開発スキルとQA知識の両方が要るので、QA経験者がコードを書けるようになると強い——「開発かインフラか」の二択の外にある選択肢として覚えておく価値があります。

🤖6. AIとの関係 — 職種ごとに違う

職種いま起きていること
開発 コードを書く作業は最も自動化が進んだ領域。残るのは「何を作るか決める」「AIの出力を検証する」側。
インフラ
第1層		 自動化の第一標的。手順書どおりの対応＝ロボットが最も得意な作業。AIが障害調査を自動で始める製品も登場済み。
インフラ
第3層		 判断が要るので残る。ただし入口ではなく到達点。「インフラだから安全」ではなく「判断する側に立てれば安全」。
QA
（手動）		 自動化が進行中。手で1項目ずつ確認する作業は減っていく。
SET
（テスト自動化）		 テストコードを「書く」作業自体は自動化されつつある。ただし「何をどう検証するか決める」のは手順化できない部分で、ここは価値が上がっている。
つまりSETという職種が消えるのではなく、SETの中の手順化された部分だけが削られる。5章の「QA経験者がコードを書けるようになると強い」は今も有効。
共通する結論: 「どの職種か」より「どの層に立つか」。
手順どおりに作業する層はどの職種でも削られ、決める・設計する・検証する層が残る。求職者のキャリア相談では、職種名の議論に閉じないこと。

📖7. 用語辞典（面談で出てきたら）

SET / SDETエスイーティー／エスデット
SET＝Software Engineer in Test（Google発祥）、SDET＝Software Development Engineer in Test（Microsoft発祥）。ほぼ同義で、出自の会社が違うだけ。意味は「テストを専門にする開発エンジニア」。
UiPathユーアイパス
RPAツールの代表格。RPA＝Robotic Process Automation。人がPCでやっている定型作業（エクセルを開く→コピー→貼り付け→保存）を記録してロボットに繰り返させる。フローチャートを組み立てる感覚で作れるので事務職の人でも扱える。国内シェア8年連続1位。
SREエスアールイー
Site Reliability Engineering（サイト信頼性エンジニアリング）。Googleが作った職種。「サービスを落とさないことを、人力の頑張りでなく設計とコードで解決する」という考え方です。
従来のインフラ運用が「落ちたら人が駆けつけて直す」だったのに対し、SREは「落ちない仕組みを作る」「落ちても自動で復旧する仕組みを作る」に発想を変えた職種。インフラの最上位層で、年収も高い。
※重要: Googleの元々の設計では「SREチームの半分以上は普通のソフトウェアエンジニアを採用する」となっています。つまりインフラの人が上がる職種というより、開発者に運用を担わせる職種として作られました。
DevOpsデブオプス
Development（開発）＋ Operations（運用）を繋げた言葉。「作る人」と「動かす人」が分断していると問題が起きるので、両者が協力する（あるいは同じ人がやる）という考え方・文化のこと。
もともとは職種名ではなく「進め方の思想」でしたが、今は「DevOpsエンジニア」という職種名としても使われます（会社によって中身がバラバラ）。実務では自動デプロイの仕組み（CI/CD）を作る人を指すことが多い。
SREとDevOpsの関係: DevOpsが「思想」で、SREが「その思想をGoogle流に実装した具体的な職種」というのが一般的な整理。ただし現場では混同されがちです。
CI/CDシーアイ・シーディー
コードを書いたら、自動でテストして自動で本番に反映する仕組み。手作業でファイルをアップロードしていた時代の作業を全部自動化したもの。この仕組み自体を作るのがDevOps/SREの主要な仕事の1つ。
プラットフォームエンジニア
開発者が使う「共通の土台」を作る職種。各開発チームが個別にインフラを触らなくて済むよう、社内向けの基盤やツールを整備する。SREの次に出てきた新しい職種名で、これも会社によって中身が違います。
NOCノック
Network Operations Center。監視室のこと。画面にアラートが並んでいて、それを見て対応する。夜勤シフトはここ。
IaCアイエーシー
Infrastructure as Code。サーバーの構成をコードで書くやり方。手作業で設定する時代から、コードで管理する時代へ。Terraform がその代表的なツール。
Kubernetesクバネティス／K8s
コンテナ（アプリを入れた箱）を何十個・何百個も自動で管理する仕組み。「1個落ちたら勝手に立て直す」ようなことを自動でやる。
AIOpsエーアイオプス
運用（Operations）をAIにやらせる流れ。アラートを受けて原因調査まで自動で行う製品が実際に登場している。
回帰テスト（リグレッションテスト）
「機能Aを直したせいで、関係ないはずの機能Bが壊れていないか」を確認するテスト。ソフトは一箇所直すと別の場所が壊れるので毎回全部確認し直す必要がある。自動化の価値が最も高い領域。
上流／下流
仕事の流れの前半と後半。上流＝何を作るか決める（要件定義・設計）、下流＝決まったものを作る・試す。求人票にも面談にも出てくる言葉です。上流ほど手順書がない＝判断の仕事。
社内SEしゃないエスイー
自社の社員のためにITを担当する職種（お客様向けに作るのではない）。パソコンやシステムの困りごと対応（＝ヘルプデスク）から、業務のやり方そのものを変える仕事（＝業務改善・DX）まで幅があります。VBAなどで自動化した経験がそのまま実績になる職種。
フロント／バック
フロントエンド＝利用者に見える画面側。バックエンド＝裏でデータを処理する側。「フルスタック」はこの両方＋インフラまで1人で通せる人のこと。
PMピーエム
プロジェクトマネージャー。何を・誰が・いつまでに作るかを決めて進行を管理する人。エンジニアのキャリアの上がり先の1つ。
VBAブイビーエー
Excelに標準で入っている自動化の仕組み（マクロとも呼ばれる）。事務職の人が独学で使っていることが多く、「自分で課題を見つけて解決した」証拠として面談で拾う価値が高い。
RPAアールピーエー
Robotic Process Automation。人がPCでやっている定型作業を、そのまま記録してロボットに繰り返させるソフト。UiPath がその代表格（国内シェア1位）。VBAより広い範囲（複数のソフトをまたぐ作業）を自動化できます。
DXディーエックス
デジタルトランスフォーメーション。業務のやり方自体をITで作り替えること。既存業務をそのままIT化するのとは違い、やり方そのものを変えるのがDX、という区別で使われます。

🎯8. 面談で使うなら

  • 「インフラ志望」と言われたら → どの層を想像しているか確認する（監視のつもりか、設計まで見ているか）
  • 「開発かインフラか」で悩んでいたら → 境界が溶けている事実を伝える（インフラもコードを書く）
  • 「AIに代替されないか」と聞かれたら → 職種でなく層の話に置き換える（手順作業は削られ、判断は残る）
  • QA・テスト経験者が来たら → SETという選択肢を覚えておく（経験がそのまま応募要件になる稀な職種）
  • 自動化ツール（VBA・UiPath等）の経験者が来たら → 社内SE・業務改善職では実績そのものになる
