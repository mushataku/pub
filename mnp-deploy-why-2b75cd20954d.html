クラウドの載せ方 ― 世の中の定石と、MNP の決着

2026-10-12（月）2:30・bot-lab の司令塔。公式文書・定番の文献の調査と、Fable の critic との3往復で決めた。前の図（今の姿と費用）: MNP の本番への載せ方

① 機能ごとに箱が違うのは普通箱を分けてよい理由は「要る道具が違う」だけ。MNP は 軽い・ブラウザ・電話 の3つにそろえる。
② 作り直さない、は正しい。手段が違う箱を細かく割るのでなく、箱の中の「層」を使い回す。割るほど版ずれが増える。
③ 段1は動いた・穴は図の外にあった着地→本番 2分07秒。失敗が無音・PC の係の遅れ・お金を払う係の版ばらばら、を先に塞ぐ。

1. 言葉の地図 ― コードが本番で動くまで

図1　作る → 載せる → 走る
コードmaster の1コミット
例 bb27b5a4
作る
build →
箱（image）コード＋Python＋ブラウザ等を一式で固めたもの
版名（tag）: git-bb27b5a4
指紋（digest）: sha256:… 中身から決まる
載せる
deploy →
置き場Service＝いつも開いている窓口業者コンソール・名義人ページ・運用コンソールJob＝呼ばれたら走って終わる係段2〜の係・重い作業の係・PayPay・LP 支払い
走る

動いている本番夜中も人がいない所で動く

世の中の呼び名: 12-Factor App の「build・release・run を分ける」。走る段は人がいない時間に自動で動くので、そこで壊れる余地を一番小さくする。一度作った箱は書き換えず、変えるときは新しい箱を作る（immutable）。

今夜の事故はここで起きた。段2〜の係（Job）は自分の箱を持たず、運用コンソールがいま使っている箱を借りていた。修正は着地していたのに運用コンソールの箱が古いままだったので、係も古いコードで3回動いた。

2. 箱の中は「層」になっている ― 作り直さない仕組み

図2　ブラウザの箱の中（下ほど変わりにくい）
⑤ 箱ごとのコード（運用画面・Job の係）週 約130回変わる
④ 共有のコード（model.py など）週 約23回
③ ライブラリ（pip で入れる部品）月に数回
② ブラウザ（Chromium）数か月に1回
① 土台（OS・Python）数か月に1回

点線＝この着地で作り直す層

④ の model.py が変わったら、④と⑤だけを作り直す。①〜③は前の箱から使い回す（--cache-from）。

決まり: 1つの層が変わると、その上は全部作り直し（Docker 公式）。だから変わりにくいものを下に置く。

実測: 業者コンソールは使い回しで「作る」が35秒。運用コンソール（約1.4GB）は今は使い回しが無く約3分。段2で使い回しを入れる。

拓也の「変わらない部品はいちいち載せ直さなくて済むように」は、この層の使い回しで実現する。箱を細かく割らなくても、変わらない層（ブラウザ・ライブラリ）は作り直されない。なお「載せる」こと自体は安くて安全（新しい版が起動しなければ前の版のまま）。高くつくのは「作る」方。

3. 箱を細かく割ると何が起きるか

図3　model.py を1回直したとき
要る道具で3つ（決めた形）
軽い箱ブラウザの箱

model.py が入る箱は2つ。どちらも同じコミットから作り、その箱の置き場すべてに同じ版を載せる。作り終わる時刻の差は1〜2分。

機能ごとに10個に割った形
業者名義人A名義人B画面作業段2申込回線LPPayPay

10個を作り直す。作り終わる時刻がばらばらで、その間は新旧が混ざる（今夜の事故の型）。作る時間は10倍近くになり、無料枠（月2,500分）を超える。

世の中の呼び名: 分散モノリス（distributed monolith）＝分けたのに一緒にしか変えられない状態。Sam Newman は「一番悪い形」と呼ぶ。Martin Fowler は「2つが繰り返し一緒に変わるなら1つに戻せ」「まず1つで始めよ（Monolith First）」。

今夜の事故を消すのは箱の数ではない。「同じコミットから作った同じ版を、その箱の置き場すべてに載せる」決まりが消す。箱の数はこれとは別の話。

軽い箱Python だけ
  • 業者コンソール
  • 名義人ページ（今の URL）
  • 名義人ページ（前に渡した URL）
1つの箱を入口違いで3か所に（今は2つの箱 → 1つに統合）
ブラウザの箱Chromium 入り

  • 重い作業の係

世の中の呼び名: 同じ箱を入口違いで走らせるのは 12-Factor の process types（Heroku の Procfile の web／worker）。普通のやり方。

5. ブラウザが要る・要らないの線

図5　MNP の段ごとに
ブラウザが要る
  • LinksMate の画面を操作する段（新規の申込・回線の追加・予約番号の発行・本人確認の画面）
  • 運用コンソールの画面から係を起こす所
要らない
  • メールを読む・保存先の読み書き・業者や名義人への知らせ
  • LP 支払い（Pixel の Google Pay）・本人確認の撮影（名義人の端末）
  • 転送の承認（HTTP の取得と送信だけで済んでいる）
問い答え理由
Chromium でないとダメかChromium のまま使っている patchright（人らしく見せる版の Playwright）は Chromium 専用。今の箱には使っていない Firefox・WebKit・2本目の Chromium が入っている（約220MB）→ 段2の後に外す。ただし軽い「headless shell」版はローチケが入口で弾いた実測がある＝本物の Chromium は残す
ブラウザ無しで申込を通せるか今はしない画面に CAPTCHA は無いので技術的には不可能ではない。ただ bot-lab は「普通の人に見える」こと（人の打鍵・マウスの動き）に投資してきた。HTTP を直接叩くと通信の指紋や JS の実行の有無で見え方が変わる＝測っていない賭け
箱を軽くすると速く起動するかしないCloud Run 公式: 箱の大きさは起動時間に影響しない。軽くして得するのは「作る」時間と置き場の容量

6. 着地 → 本番（決めた形）

図6　人が撃たない載せ方（段1で業者コンソールは実際に動いた）
1 着地master に入る
→
2 関係する箱だけ起きる中に入れるファイルの一覧は Dockerfile から機械で作る
→
3 作る層を使い回す
→
4 試す赤なら止めて Discord へ即知らせ
→
5 柵いま載っている方が新しければ載せない
→
6 全部の置き場へ同じ版Job は指紋（digest）で指す
→
7 確かめる新しい版が起動したか。違えばやり直す

実測（段1・業者コンソール）: 着地 01:59:11 → ビルド開始 +31秒 → 本番で新しい版が動く 02:01:18。2分07秒。docs だけの着地では起きないことも確かめた。
保険: 1時間に1回クラウドの見張りが、各箱の最新のビルドと載っている版を比べ、ずれていれば作り直しを起こす（PC が寝ていても回る）。

Job は指紋で指す理由: Service は載せたときに版名を指紋に固定するが、Job は走るたびに版名を引き直す（Cloud Run 公式）。しかも同じコミットから作り直すと指紋が変わることを今夜実測した。版名で指すと、次に走ったとき黙って別の箱を引きうる。

7. critic が見つけた、設計図の外の穴

① 失敗が無音　試験が赤だと本番には載らないが、誰にも知らされない。→ 段1.5 で、失敗・柵で止まった・判定できなかった を Discord に即知らせる。
② PC の係の遅れ　PC で動く係の多くは走るたびに最新を取り込むが、LinksMate の転送の押し出し係は 433コミット遅れのまま数分おきに動いている。誰も使っていない古い checkout も残っている。→ 別の票で直す。
③ お金を払う係が版ばらばら　電話の箱には LP 支払い（Google Pay）の係が乗っていて、同じ箱の3つの係が3つの別の版で動いている。→ 段3-D でそろえる。自動で新しい版に入れ替わるようになるが、払ってよい条件（額の範囲）は変わらない。

8. これからの段

段やること順番
1GitHub と Google Cloud をつなぎ、業者コンソールを自動に済（2分07秒）
1.5共通の門: 手順を1枚にまとめる・失敗を Discord へ・柵を強くする・止めたいときのブレーキ次（これだけ先）
2ブラウザの箱: 運用コンソール・重い作業の係・段2〜の係を同じ版で。借りるのをやめる。層の使い回し1.5 の後に3つ同時
3-AB軽い箱: 業者コンソールと名義人ページを1つの箱に
3-D電話の箱: 3つの係を同じ版で。repo 全部を入れるのをやめる
4クラウドの見張り（毎時・ずれたら自分で直す）。deploy.sh は「設定を変える専用＋緊急用」に2・3 の後
別PC の係の取り込み／共有データの形の番人（古い形を新しいコードで読めるか）／ブラウザの箱を軽くする今すぐ（軽くするのは2の後）

費用: 見込みは月1,700〜2,400分で、無料枠2,500分の内側だが余白は薄い。超えても1,000分あたり約900円で、承認済みの月1,000円の内。軽い箱を1つにすると名義人ページの作り直しが消えて月200〜300分減る。予算の知らせ（50%・90%・100%）は張ってある。
名義人ページは業者コンソールと同じ箱になるので、業者コンソールの着地のたびに入れ替わる（1日数回）。中に記録を持たないページなので、使う人から見た動きは変わらない。

2往復目で増えたのは、論点が細かく割れたから（大きな異論が減り、細部の選び方が並んだ）。前任の設計の骨（箱ごとの自動・中に入れる一覧は Dockerfile から機械で作る・版名はコミット・柵3つ・箱は3つ）は保たれた。

critic の指摘で変わった点（18）
  1. 「1本の流れで全部作り、指紋が変わった箱だけ載せる」案を捨てた（中身が同じでも指紋が変わると実測・費用も月約2,200分増）
  2. 失敗の知らせを段1.5 に前倒し。形は新しいサービスを立てず、手順の中から Discord の webhook へ。鍵は bot の全権の鍵でなく、1チャンネルに書けるだけの webhook
  3. 柵の手順を1つのファイルに（段2・3がコピーして門が4つに分かれる前に）
  4. 柵を「読み直す」でなく「載せた後に確かめて、古ければやり直す」形に（並走で古い方が勝つ隙間を閉じる）
  5. 柵が見る「いま載っている版」を、起動に成功した版から読む（同じ repo に既に注記があった罠）
  6. 柵が判定できなかったときに印を出して知らせる（壊れた門が成功に見えない）
  7. Job は差し替えても起動の検査が無い＝載せる前に箱の中で各入口を読み込んでみる
  8. Job は指紋で指す
  9. 電話の箱の置き場に LP 支払いの係を名指し
  10. PC の係を版ずれの場所として数える（別票）
  11. フォルダごと入れる行は「フォルダ/**」で見張ってよい、を規則に
  12. 軽い箱の統合を費用の根拠でも裏づけ（月200〜300分）／費用の余白が薄いことを明記
  13. 見張りを「鳴る」から「自分で直す」へ
  14. 止めたいときのブレーキ（サービスに印を付けると自動で載せない）と、戻すのは「git で元に戻す着地」が正、を明文化
  15. 箱ごとの設定ファイルを分け、段2・3を同時に撒けるように
  16. ブラウザ無しの申込を見送る根拠を「測る前に対策しない」に結んだ
  17. 見張りは git を持たず、ビルドの記録・載っている版・GitHub の比較で前後を決める（同じ版を6時間に1回までしか撃ち直さない）
  18. 箱の中のメモリ上の記録は入れ替わりで消える前提、を明文化

critic の側が引いた点: 「箱を軽くすると起動が速くなる」（Cloud Run では無関係）／「** は禁止」（推奨だった）／無料枠の数え方（月2,500分）。
