reCAPTCHA の即時通過の朝→夕方の落ち込みは、鍵でも経路でもなく時間で戻った（2026-11-18 夜・4マスの同時対照）

GCP→家（PC が exit node）×鍵 fresh2×公開の的の即時通過は、09:24 に 13/16、12:09 に 6/16、15:28 と 16:58 には封じの5腕を合わせて 3/40・1/40 まで落ちました。今夜 18:51〜20:37 に、同じ経路と、PC 直の3マス（鍵 fresh2 の公開／手元の的・鍵 fresh の手元の的）を交互に撃つと、4マスとも 13〜16/16 に戻っていました。

1. 結論

  • 落ち込みは時間で戻った: 同じ経路・同じ鍵・同じ封じ（全部塞ぐ）で、16:58 の 1/40 → 今夜 13/16。差 +0.79（95% 区間 +0.52〜+0.91）。
  • 今夜は鍵・的・経路の差が見えない: 鍵 fresh − fresh2 は +0.06（−0.14〜+0.28）、公開 − 手元は 0.00（−0.23〜+0.23）、PC 直 − GCP→家は +0.13（−0.13〜+0.37）。どれも区間が 0 をまたぐ。
  • 今夜の GCP→家は朝と同じ高さ: 09:24 の 13/16 と今夜の 13/16 の差は 0.00（−0.27〜+0.27）。
  • したがって 15:28〜16:58 の低さは、鍵 fresh2 の汚れでも家の出口 IP の評判でもなく、その時間帯の何か（Google 側の時間の変動）に乗っていたと読むのがいちばん素直。翌朝 06:00 にもう1回撃って、朝の高さを確かめる（予約済み）。

5. 黒7a の 132MB

黒7a の 15:51〜15:54 の rmnet1 の 132MB 増を、端末の dumpsys netstats --uid で読みました（端末の鍵を握って読むだけ・Wi-Fi に触らない・人材の SMS 係は前後とも ok・保留 0）。uid の記録は2時間刻み（15:00〜17:00 の1つの箱）なので、3分の窓までは絞れません。

その箱のモバイルの量は、ほとんどが Tailscale（com.tailscale.ipn）の 80.1MB 受信・79.1MB 送信でした。受信と送信がほぼ同じ量なのは、端末が中継役（exit node）として通信を素通ししたときの形です。次に多い adb のシェルの量も約 1MB でした。前の票の段B（黒7a を出口にした診断と撃ち・15:40〜15:47）の通信が、この 132MB の正体と読めます。

6. 撃ち方と置き換えたマス

  • 置き換えたマス: 票の4マスのうち「GCP→家×fresh」は撃てません。鍵 fresh は公開の的のドメインを登録しておらず、Google の応答が「Invalid domain for site key」でした。そこで PC 直×fresh2×手元の的に置き換えました。(c)−(b) で鍵の差、(a)−(d) で経路の差、(a)−(b) で公開／手元の的の差を見ます。
  • 撃ち方: 段1＝(d) と (c) を同時に各8、段2・段3＝(a) と (b) を同じ走りで交互に各8（新しい口 --cells）、段4＝段1と同じ組。fresh2 は PC と Job で重ねていません。
  • 計画外の追加: 段2の外側の待ちが10分で切れ、段2も止まったと見誤って追加の4回ずつ（19:29〜）を撃ちました。実際には段2は最後まで撃って行を押していたので、段2の後半と追加の4回ずつが同じ PC・同じ鍵 fresh2 で重なりました。追加の行は表の最後に別に載せ、本集計（各 n=16）には入れていません。入れても (a) 19/20・(b) 18/20 で、結論は変わりません。

7. 元に戻したもの・翌朝

  • PC の exit node の広告を外した・routes を API で空にした（advertisedRoutes: []・enabledRoutes: []）
  • Job の env の名前は撃つ前と同じ（RECAPTCHA_MIRROR_KEY・RECAPTCHA_MIRROR_SITE_KEY）・回ごとの上書きだけ使った
