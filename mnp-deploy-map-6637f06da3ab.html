MNP の本番への載せ方 ― 今と、目指す形

2026-10-12（月）0:50 時点の実測。bot-lab の司令塔が作成。数字の出どころは本番の設定と過去7日のビルドの記録。

続き（なぜこの形か・世の中の定石・critic との決着）: クラウドの載せ方の定石

箱（image）プログラムと、それを動かすのに要るもの（Python・ブラウザ等）を一式で固めたもの。
作る（build）コードから箱を作る。重い箱ほど時間がかかる。
載せる（deploy）本番の置き場に「次からこの箱で動いて」と渡す。

1回のコード変更で、いくつかの置き場が同時に変わるのは普通です。問題はそこではなく、それを人が手で、正しい順番で撃っていることと、1か所だけ箱を「借りている」ことです。

今の問題
  1. 着地しても本番は変わらない。誰かが①〜⑥を撃つまで、古いコードのまま動く。撃つ人は、どの変更がどの箱の中身を変えるか、どの順番かを覚えている必要がある。
  2. 段2〜の係は箱を借りている。③→④の順を守らないと、新しいコードが載らない。どの版で動いているかも名前で分からない。
  3. GitHub と Google Cloud がつながっていない。だから「着地したら自動で作る」ができない（つなぐのは初回だけの作業）。

壊れたものを載せないための柵
  • 試験が赤なら載せない（今 deploy.sh の頭で回している試験を、そのまま作る係の中へ移す）。
  • サービスは新しい箱が起動しなければ、前の版のまま動き続ける（Google Cloud の性質）。係（Job）は作った箱で読み込みの試験をしてから差し替える。
  • 着地が続くと作る係が並んで走る。古い版が後から新しい版を上書きしないよう、載せる直前に「いま載っている版が自分より新しくないか」を見る。
  • 保険の見張り：1時間に1回、7か所の版名が master の最新と合っているかを見て、ずれていたら知らせる（出来事起点が本体・定期は保険、の規則どおり）。
人の手が残るところ（めったに無い）
  • 秘密の値・権限・ログイン画面（IAP）の設定を変えるとき：今の deploy.sh を「設定を変える専用」として残す。毎回の箱の差し替えでは触らない。
  • 緊急で手で載せたいとき：今の deploy.sh は残す（今と同じ門＝遅れた木・未着地のコードでは撃てない）。
  • GitHub と Google Cloud をつなぐ初回：Chrome で機械が押す。GitHub が本人確認（パスワード・2段階認証）を求めたら、そこだけ拓也。

図の外：PC で動く係（本体の木）は今回の範囲に入れていない。必要なら同じ形で後から足す。
