1 世の中の呼び名と既製品

取引先グループの全発言を溜めて、承認つきで返す既製品は見つかりませんでした（2026-11-03 に一次の資料で確認）。自前で作るのは妥当です。作る量は、受け口150行級の部品と、読み口のアダプタまでに収めます。

bronze 層

生のまま溜める層。データ基盤の定石（medallion）では、これを正本にして、整えた表は後段で作ります。今回の GCS がこれに当たります。

送信台帳

こちらから送った内容を、送る前と後に記録する帳面（outbound audit log）。「transactional outbox」は DB 書込と配信を一緒に成立させる型の名前で、別の話なので使いません。

冪等（べきとう）

同じ通知が何度届いても、保存されるのは1回分になること。LINE の再送で二重に溜まらないために要ります。

「イベント起点」「dry-run」「SSOT」は武者野さんが既に持っている語彙です。ほかに、統合受信箱（複数のチャットを1つの受信箱で読む）と、人の承認つき送信（送る前に人が見て OK を出す）という呼び名があります。

定番の手

  1. 署名検証（LINE から来た通知か確かめる）
  2. 2xx を早く返す
  3. webhookEventId で冪等に保存
  4. 後段で処理

LINE 公式も、非同期処理と重複排除を勧めています。再送は既定で OFF で、届く保証はありません。

既製品あるもの足りないところ
LINE 公式の MCP サーバ（line/line-bot-mcp-server・preview）送信・照会・リッチメニューの13ツール受信履歴を読む口が無い
LINE の API そのもの—webhook を受けた後で本文を取り直す API は無いと明記。受けた瞬間に溜めるしかない
Chatwoot（OSS の統合受信箱）LINE 対応1対1 専用。グループは今後も対応しないとメンテナが明言
Freshchat—グループ非対応
Zendesk・チャネルトーク—グループの記述なし

3 型：受ける・溜める・読む・書く

3.1 受け口は事業に1つの小箱。OA を足してもデプロイ不要

箱は事業に1つ

Cloud Run の小箱で、URL は /line/<oa>/webhook（1チャネルに webhook は1本）。SA（プログラム用の身元）に渡す権限は、バケットへの書き込みと、line- で始まる Secret の読み取りだけ。顧客向けの既存の箱には差しません。その箱の穴1つが LINE の送信全権になるためです。

既に箱がある OA

recruit・line-bot は、自分の handler から部品の record() を呼びます（1チャネルに webhook は1本しか登録できないため）。

鍵は名前で引く

Secret Manager に line-<oa>-channel-secret と line-<oa>-channel-id。受け口は実行時に引き、署名が合わなければキャッシュを捨てて1回だけ引き直します（secret の再発行は即時置換で、新旧2本を受ける期間が無いため。再送 ON が数秒の隙間を埋めます）。権限（IAM）は事業で1回、line- 接頭辞の条件つきで付けるので、OA ごとの権限工程はありません。

長期トークンを持たない

channel ID と secret からステートレストークン（v3・15分）を発行し、約14分キャッシュします。secret は全権（短期トークンも secret だけで出る）なので、守るのは secret の置き場と、触れる主体だけです。

3.2 溜めるのは、LINE が送ってきた形のまま

<oa>/YYYY-MM-DD/<epoch_ms>_<webhookEventId>.json受信。LINE が送った形のまま（ナゲバンの今の並びと同じ）
<oa>/sent/YYYY-MM-DD/<ts>_<retryKey>_{intent|result}.jsonAPI 送信の台帳。送る前に intent、送った後に result
<oa>/oam/YYYY-MM-DD/<ts>_<messageId>.jsonOA Manager から回収した分（recruit の夜間回収の出力先を足す）
<oa>/media/<messageId>画像・ファイル・動画・音声の本体
<oa>/names/<group|user>/<id>/<ts>.json名前の観測。変わったら観測ごとに1つ、読み口が最新を取る
<oa>/repair/<messageId>.json本体の取り直し待ち。受け口が失敗した瞬間に作る
  • 再送は ON が必須です。既定は OFF で、コールドスタート（眠っている箱の起動）で test が落ちた実測があります。取りこぼしの最後の網です。
  • 検索用の表（Firestore など）は派生です。recruit の Firestore は投影として残し、BigQuery は要るときに GCS の外部テーブルで後から載せます。
  • 保持と削除：グループの受信は自動削除なし。1対1 の本体は既定 OFF（事業が opt-in）。消すのは持ち主の明示コマンドだけで、消した記録を残します。年限は事業ごとの1行です。
  • 名前が取れない発言は、構造上出ます（未認証 OA は members/ids が使えず、プロフィール利用に同意していない人は source に userId が無い）。読み口は「取れなかった」と「LINE が渡していない」を分けて出します。

▼ 1本の時系列に並べる

  • Discord と同じ口・同じ JSON です。--list で OA ごとのグループと最後の発言が出ます。
  • 中立モデル Message に attachments・kind（message/join/unsend…）・direction（受信／API送信／OA Manager）を optional で足します。Discord も添付を持つので、中立の拡張です。
  • 読む身元は操作者の ADC（その人自身の Google ログインを、道具がそのまま使う仕組み）です。PC は持ち主の gcloud、クラウドは既定どおり同等の鍵で、今の recruit・ナゲバンと同じ読み方。身元は新しく集めません。読み口は secret を要求せず、バケットの読み取り権限だけで動きます。
  • adapter が GCS を読む認証の形（REST＋ADC トークンか google-cloud-storage か）は、W1 で chat-bridge の依存宣言の場所と一緒に決めます。

3.3b 台帳と導線：どの OA も同じ1コマンドで読む

武者野さんの依頼（20:05）「作った公式ラインが溜まっていって、それを取り出す口とその引き方」への答えです。

  • 台帳は全事業で1つ：chat-bridge の line_oa.toml。列は、表示名・ベーシック ID・事業・repo・GCP プロジェクト・置き場（型＝gcs:<bucket>/<oa>/、移行前＝firestore:line_group_messages・cloud_logging:line-bot）・受け口 URL・読む身元（持ち主の gcloud アカウント）・状態（稼働／移行待ち）。各 repo の IDS にある OA の行は、台帳への1行のポインタに置き換えます（値を写しません）。
  • 読む身元を台帳に持つ理由：11/3 に、PC の ADC が人材側のアカウントで、bot-lab 側のバケットに 403（権限なし）でした。OA ごとに「どのアカウントで読むか」が違うので、読み口は台帳の列から gcloud auth print-access-token --account <持ち主> を選びます。
  • どの OA でも同じ1コマンド：python -m chat_bridge.cli.fetch --channel line:<OA名>/<グループ>。--list で、台帳にある全 OA とグループ、最後の発言が出ます。移行前の OA（recruit の Firestore・line-bot の Cloud Logging）も、読み口の中の移行用の読み手で同じ形に出します（W4・W5 が着地したら消す）。今日から全 OA が1つの口で読めます。
  • 導線：読む口の skill（「LINE 読んで」「公式LINE のグループ見て」「取引先の LINE」で発火）→ 台帳 → コマンド。line-oa-open と、運送のグループを読む既存の skill も、ここを指します。全置き場の地図（store_map.py）にも台帳を1行足します。
  • 開設の最後に台帳へ1行足します（up の Z）。台帳に無い OA は読み口に出ないので、足し忘れは audit が赤で知らせます。
  • ナゲバンが最初の利用者です。それまで、新しい OA に専用の口（受け口・読み口）は作りません。

  4. 武者野さんが1通ごとに承認
