LP 購入の決済を、機械で押し切る2つの道

A: 専用 iPhone で Apple Pay ／ B: いまある Pixel で Google Pay。どちらも図で「誰が・何を・どの順で」を見せます（2026-10-10）

ひとことで

LinksMate の LP 購入は、いまゆうとが自分の iPhone の Apple Pay で毎回手で払っています。前日型の依頼で一番時間がかかる段で、10/9 は LP の依頼から入金まで 2時間24分でした。この段を機械で押し切る道が2つあります。

道A：専用の中古 iPhone を、ESP32 という小さな基板で操作する（目安 約1.7万円）。
道B：いまある Pixel 7a を adb で操作して Google Pay で払う（0円）。

推奨は「まず B を費用0で1回試す」。Apple Pay でなければならない理由が出たときだけ A に進みます。

① 今の流れ：LP の購入だけが人の手

ゆうとが手で払っているのは、購入画面の Apple Pay がlinksmate.jp の確認画面の中で決済まで終わる作りで、決済だけの URL を作って渡す手が無いからです。PC の Chrome では Apple Pay のボタンも使えません（どちらも 2026-09-22 の実測）。購入画面の支払い手段は、コンビニ・銀行・クレジットカード・Apple Pay・Google Pay の5つです。

コンビニ・銀行は払い込みが要り、手数料もかかります（346円・330円）。Apple Pay とカードは手数料なしで、反映まで約5分です。

② 2つの道が同じ土台に立つ理由：カード番号を「端末専用の番号」に置き換える

  • Apple 側：Apple は元のカード番号を保存せず、端末の Secure Element が「端末アカウント番号」と取引ごとの動的なセキュリティコードを出す、と Apple が書いています。 公式で確認
  • Google 側：実際のカード番号の代わりにランダムな番号の「仮想カード」を店に渡す、と Google ウォレットのヘルプにあります。 公式で確認
  • 3D セキュア（カード会社の追加確認）が出にくい理由：Google Pay API には、カードの持ち方が2種類あります。「端末トークン」（CRYPTOGRAM_3DS＝端末で作る暗号つき）と、「Google アカウントに保存したカード番号」（PAN_ONLY）。後者は3D セキュアなどの追加確認を求められうる、と Google の開発者ブログにあります。端末に入れたカードなら追加確認が省かれることが多い、という筋です。 公式で確認
  • ただしLinksMate の決済がどちらの方式を受け付けるかは測っていません。JCB は端末トークン方式に未対応と Google の資料にあるので、カードのブランドも結果を左右します。 未測定

③ 道A：専用の中古 iPhone を ESP32 で操作する

流れ（誰が・何を・どの順で）

  1. 人・最初の1回 専用の iPhone に専用の Apple ID を作り、決済に使うカードをウォレットに入れる。
  2. 人・最初の1回 確認を指でなくパスコードにする。iPhone SE（第2世代）のような Touch ID 機種なら、設定の「Touch ID とパスコード」で Apple Pay のスイッチをオフにする（Apple が「Touch ID を Apple Pay でオン・オフできる」と書いています）。Touch ID 機種は支払い確認が「Touch ID またはパスコード」で、サイドボタンの2回押しが要りません。公式で確認
    Face ID 機種は「サイドボタンを2回押してから顔かパスコード」。2回押しの代わりに AssistiveTouch で確認できる、と検索結果にありましたが、Apple の本文を取得できず確かめていません。未確認
  3. 人・最初の1回 iPhone の AssistiveTouch をオンにし、ESP32 をマウスとキーボードとしてペアリングする（Apple はポインタ機器を AssistiveTouch につなぐ手順と、Bluetooth キーボードのペアリングを書いています）。公式で確認
  4. 機械 Safari で LinksMate のタイプB 口座にログインし、LP 購入の画面で額を入れる。
  5. 機械 Apple Pay を選び、支払いシートに出たパスコードを入れる。キーボードで入らなければ、マウス役でテンキーを1つずつ押す。
  6. 機械 画面は AirPlay で PC に届くので、支払い完了の表示を読んで次へ進む。

機械の部品：実在を確かめたもの

  • 手：ESP32 を Bluetooth のキーボードやマウスにする Arduino 用ライブラリ — ESP32-BLE-Keyboard、ESP32-BLE-Mouse、両方入りの ESP32-BLE-Combo。Keyboard と Combo の README は「iOS は安定しない・古い端末では動かない」と書いています。
  • 目：AirPlay 受信ソフト UxPlay。iOS の画面ミラーリングを受けられ、Windows 向けは MSYS2 でビルドする形です（配布済みの実行ファイルは確認できませんでした）。保護された動画は映りません。

費用の目安

中古 iPhone SE（第2世代）が約1.5万円、ESP32 が約2千円。合計で約1.7万円です。中古の相場は状態と容量で幅が大きく、価格比較サイトでは約0.4〜1.8万円でした（2026年7月時点）。ESP32 の国内の店頭価格は確かめていない目安です。

安全の注意：人がいなくても払える端末になります。決済のカードは上限つきのプリペイドかバーチャルカードにして、万一のときの被害の上限を先に切っておく前提です。

道Aの「まだ測っていない」5つ 要実機確認

  1. Touch ID の Apple Pay をオフにすると、支払いシートが本当にパスコード入力になるか（公式の文面は「Touch ID またはパスコード」まで）。
  2. ESP32 の Bluetooth 操作で iPhone を安定して動かせるか（ライブラリ側が「iOS は不安定」と書いている）。
  3. 支払いシートのパスコード欄に、Bluetooth キーボードで入れられるか。入らなければマウス役でテンキーを押す。
  4. AirPlay の画面に Apple Pay の支払いシートが映るか。
  5. Windows の AirPlay 受信（UxPlay のビルド）が、止まらず動き続けるか。

④ 道B：いまある Pixel で Google Pay

流れ（誰が・何を・どの順で）

  1. 人・最初の1回 Pixel の Google ウォレットに、決済に使うカードを入れる（この Pixel にいまカードが入っているかは未確認）。
  2. 機械 PC が adb で Pixel の Chrome を開く。Pixel の Chrome を CDP で動かす前例は、すでにあります（ローチケの Android 腕）。
  3. 機械 LinksMate にログインし、LP 購入の画面で額を入れ、支払い手段の「Google Pay」を選ぶ。
  4. 機械 出てきた支払いの確認を通す。ここが「画面ロックの PIN を adb で入れられるか」の核心（下の未測定②）。
  5. 機械 支払い完了を読んで、申し込みを先へ進める。

Pixel の PIN について、すでに分かっていること

  • Pixel のロック画面は、機械が PIN を adb で入れて解く仕組みがすでに実運用で動いています。設定アプリの「本人確認」画面（端末の PIN を求める画面）に PIN を打つ口もあります。
  • 既知の罠：input text が PIN パッドに入らない機種があり、その場合はinput keyevent 8 9 10 11（数字キー1〜4）が回避策、と記録されています。この Pixel 7a のロック画面では input text で解けています。
  • PIN の誤入力を続けるとロックアウトされるので、失敗の記録と冷却の仕組みが付いています。
  • Google Pay の支払い確認の画面で同じ入れ方が通るかは、まだ測っていません。

道Bの「まだ測っていない」3つ 未測定

  1. ① 3D セキュアが出ないか：LinksMate の Google Pay で、カード会社の追加確認が出るか（②の土台の「端末トークンなら省かれる」が、ここで成り立つか）。
  2. ② 支払い確認の画面ロックを adb で通せるか：求められるのが PIN なら、上の既知の入れ方で通る見込み。指紋だけを求められたら、機械では通せません。
  3. ③ 支払いシートを機械が読めて押せるか：調べていて見つけた3点目です。Google Pay の支払いシートは、Chrome の中でなく OS 側の画面らしい（推測）。そうなら CDP では見えないので、adb の画面ダンプで読めるかを測ります。

測り方：次の LP 依頼で、1回だけ手で Pixel から払ってみる

  1. 人 次の依頼の LP 購入を、Pixel の Chrome から Google Pay で手払いする。
  2. 見ること：(a) 3D セキュアの画面が出たか (b) 支払いの確認で何を求められたか（PIN・指紋・何もなし） (c) その画面を adb のダンプで読めたか。
  3. この3つが分かれば、B を機械化できるかが決まります。費用は0円です。

⑥ 拓也が決めること（3つ）

  1. どちらの道か推奨は「まず B を1回手で試す」。B の測定結果（3D セキュア・支払い確認・画面の読み取り）を見てから、A に進むかを決められます。
  2. A を選ぶなら、購入の承認（課金）中古 iPhone と ESP32 で約1.7万円。B だけで足りるなら不要です。
  3. 決済カードを誰のものにするかいま手払いに使っているカードをそのまま載せるか、上限つきの専用カードを新しく作るか。機械が払える端末になるので、専用カードで被害の上限を切るほうが安全側です。どちらの道でも同じ問いです。

⑦ 根拠リンクと、確かめきれなかったこと

公式の根拠

  • Apple：Apple Pay で支払う（Touch ID 機種は Touch ID かパスコード／Face ID 機種はサイドボタン2回押しから）
  • Apple：iPhone と iPad で Touch ID を使う（Apple Pay での Touch ID のオン・オフ）
  • Apple：Apple Pay のセキュリティとプライバシーの概要（端末アカウント番号と動的セキュリティコード）
  • Apple：AssistiveTouch でポインタ機器を使う、iPhone で Bluetooth キーボードをペアリング、iPhone SE（第2世代）の仕様（Touch ID 搭載）
  • Google：お支払い情報の保護（仮想カード・画面ロック）
  • Google：Google Pay API の認証方式（PAN_ONLY と CRYPTOGRAM_3DS）、どちらで追加確認が要るか
  • 相場：iPhone SE（第2世代）の中古相場（価格比較サイト・2026年7月時点）

確かめきれなかったこと

  • Face ID 機種で、Apple Pay の Face ID を切る設定と、AssistiveTouch の「確認」でサイドボタン2回押しを代える設定（Apple の本文を取得できなかった）。
  • Touch ID を切ったあとの支払いシートの挙動、Bluetooth キーボードでのパスコード入力、AirPlay の画面に支払いシートが映るか（すべて実機でしか分からない）。
  • LinksMate の Google Pay の作り（Apple Pay 側は確認画面の中で完結すると実測済み。Google Pay 側は未確認）。
  • ESP32 の国内の店頭価格。中古 iPhone の店ごとの在庫価格。
