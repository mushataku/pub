三田さんへ: line-bot の始め方

三田さんが line-bot に最初の PR を出すまでの 1 枚です。言葉の意味: 殻＝claude.ai/code で line-bot を開いたときのセッションの環境、基盤＝拓也の Claude が使う仕組みとデプロイを決めるファイル、門＝本番に出る前の最初の検査、番人＝殻で間違えやすい操作を止める仕組み、札＝Issue のラベル、コネクタ＝claude.ai と GitHub をつなぐ接続。細かい決まりは repo の docs/CONTRIBUTING.md にあります（repo は private なので、招待を受けてから開けます）。

自分の PR は、三田さん自身でマージしてよい（マージ＝本番に出る）。触らないのは拓也の基盤だけ。

拓也の確認は要りません。触らない拓也の基盤は、.claude/・.github/・docs/instructions/・どの階層でも CLAUDE.md・cloudbuild.yaml・Dockerfile・docs/TODO.md・門と見張りの script 4 本（5 章に全部あります）です。

基盤に触れる変更が要るときは、自分でマージせず PR を出して、LINE の作業グループで拓也に頼んでください（拓也がマージし、門の解除も拓也がします）。触れたままマージすると、本番の入口の門が止まり、拓也と三田さんのデプロイが両方止まります（1 章）。

main への直接の push と、GitHub の Web 画面での main のファイルの直接編集はしません（PR が記録になります）。Approve も使いません。

図1: 基盤に触れたままマージしたときに起きること（赤＝止まる）

line-bot は main が更新されると、そのまま本番の LINE Bot にデプロイされます。ドライバーが配送中に使っているので、デプロイの最初の段にある門で検査しています。

基盤は、拓也の Claude が動くための仕組み（.claude/ や CLAUDE.md）と、デプロイそのものを決めるファイル（cloudbuild.yaml・Dockerfile・門と見張りの script）です。ここが三田さんの更新で変わると、門は本番に出しません。止まったデプロイは拓也が解除するまで止まり続けるので、拓也の修正も出せなくなります。

基盤の外（アプリのコード・テスト・docs/SPEC.md・docs/KNOWLEDGE.md・requirements.txt）は、三田さんが自分でマージして本番に出して大丈夫です。

2. 全体の流れ

  1. 三田さん仕事を決める札が 実装OK の Issue か、小さな修正
  2. →
  3. 三田さんの Claude枝で実装・テストkodai/…
  4. →
  5. PR の前自己レビューdiff だけをサブエージェントに見せる（6 章）
  6. →
  7. 三田さんPR を出す本文に pytest の出力と所見。URL を作業グループに 1 行
  8. →
  9. 三田さん自動レビューを読む拓也の routine が付ける所見のコメント
  10. →
  11. マージの直前main を取り込み、pytest で緑を確認rebase か Update branch
  12. →
  13. 三田さん自分でマージこの時点で本番に向かう
  14. →
  15. Cloud Buildテスト赤なら本番に出ない
  16. →
  17. 本番/version の sha を見るマージのコミットになれば完了

図2: 青が三田さんの番、緑が自動の段。最後まで三田さんが見届ける

PR を出すと、拓也の claude.ai の自動レビューが所見のコメントを 1 件付けます。承認ではないので、気になる所見だけ直せば十分です。自己レビューの所見と合わせて読んでから、マージします。Approve は自分の PR には要らないので使いません。

マージの直前に main を取り込む理由は、PR の試験（Actions）が 2026 年 12 月 1 日まで止まっていて、機械が最初にテストするのはマージの後の Cloud Build だからです。取り込みは、三田さんの Claude が自分の枝の上で git fetch origin && git rebase origin/main の後に git push --force-with-lease origin kodai/… でやるか、GitHub の Update branch ボタンでもかまいません。そのうえで python -m pytest -q -m "not integration" を撃ち、緑を確かめてからマージします。

マージのしかたは、マージボタン・gh pr merge・GitHub コネクタのどれでもかまいません。マージ後は Cloud Build のテストが走り、赤ならデプロイされません。しばらくしても本番の /version の sha がマージのコミットにならないときは、デプロイが止まっています（deploy-failed の Issue が立つこともあります）。直す PR か revert の PR を出してください（URL は docs/CONTRIBUTING.md §8）。docs だけの変更は本番のビルドが起きないので、/version は変わりません（それで正常です）。

main に赤のコミットが残ると、拓也のデプロイも止まります。直す PR か revert の PR（7 章）を出して、自分でマージしてください。

3. 最初の 1 本（殻の確認 PR）

最初の PR は、ドライバーに見えない「殻の確認」です。殻は claude.ai/code で line-bot を開いたときのセッションの環境のことで、三田さんの殻でも line-bot の仕組み（起動の案内と、間違えやすい操作を止める番人＝5 章）が働くかを測ります。この PR は docs だけの変更なので、本番のビルドは起きません。三田さんが自分でマージします。

  1. 招待を受けて line-bot を開くGitHub の招待を受けたら、claude.ai/code で mushataku/line-bot を開きます。repo の一覧に出てこなければ、作業グループに書いてください（拓也側の設定で直します）。
  2. 環境変数を足す 任意claude.ai の環境設定に LINEBOT_GUEST=1 を足すと、起動時の待ち 20 秒が消えます。起動時に「拓也の殻か三田さんの殻か」を見分けるため最長 20 秒待っていて、足すと三田さんの殻だとすぐ決まります。足しても害はなく、足さなくても約 41 秒で動きます。
  3. Claude に頼む「docs/CONTRIBUTING.md の §2 にある殻の確認の 6 項を測って、kodai/0-shell-check から PR を出して」と頼みます。Claude は最初に切られた claude/… の枝から git switch -c kodai/0-shell-check で切り直します。止まるはずの操作は全部 --dry-run か取り消せる形で撃ち、本物の main への push はしません。止まらなかった操作で変わったものは push せずに捨てます（捨て方は docs/CONTRIBUTING.md §2 の項目 3）。PR は Create PR ボタンで出します（claude.ai/code の GitHub の通り道が gh pr create の GraphQL を通さないことがあります）。ボタンが出ない・claude/… の枝から出そうになるときは、Claude に REST（POST …/pulls）で kodai/0-shell-check から出させます。
  4. PR に表を貼る差分は結果の表を書いた 1 ファイル（docs/shell-check/kodai.md）だけです。PR 本文にも同じ表（項目・期待・実測・コマンドと出力の要点）を貼り、PR テンプレートの残りの欄も埋め、テストの欄には撃った pytest の出力を貼ります（本文は Claude に REST の PATCH …/pulls/<番号> で書かせても、Web 画面の PR 本文の編集で直してもかまいません。本文の編集は main を変えません）。止まった操作は止まった文言を、止まらなかった操作はそのまま書けば正解です。
  5. 作業グループに URL を 1 行、そして自分でマージいつも拓也と依頼をやり取りしている LINE の作業グループに PR の URL を貼ります。自動レビューの所見のコメントを読み、2 章の手順（main を取り込んで pytest）の後で、三田さんが自分でマージします。
  6. 次の 1 本殻の確認 PR をマージしたら、Issue #6 に進みます。LINE の送信や AI の月の上限に当たったとき、いまは黙って失敗しているので、それを知らせる仕組みとドライバーへの一言を足す仕事です（札 実装OK）。

4. 枝（branch）と Issue の札（label）

使う枝

  • kodai/<番号>-<話題>
  • 例: kodai/6-limit-alert（番号は Issue の番号。Issue が無い小さな修正は 0）

使わない枝

  • main
  • claude/…（誰が作ったものでも拓也の機械が毎時片付ける。claude.ai/code が最初に切る枝もこれなので切り直す）

図3: 三田さんの枝は kodai/ で始まるものだけ

GitHub の Revert ボタンが作る revert-… の枝だけは例外で、ロールバック（7 章）に使ってかまいません。消さずに置いておいてください。

Issue の札は 2 つです。設計判断待ち は拓也の答え待ちで、まだ実装しません。実装OK が付いたら実装してよい合図です。

ドライバーの操作が変わる・新しい外部サービスやお金が要る・優先順位が絡む、のどれかに触れるなら Issue で拓也に聞いてください。触れない小さな修正は Issue なしで PR から直接で構いません。

5. 番人が止める操作

番人が止める（Claude の操作）

  • main への直接の push
  • kodai/ 以外の枝への push と、kodai/ 以外の枝の削除
  • [skip ci] などの印つきの commit
  • Approve（自分の PR には要らない）
  • PR を経ないマージや ref の更新（API で直接）
  • 基盤のファイルの編集（.claude/・.github/・cloudbuild.yaml・Dockerfile・どの階層でも CLAUDE.md・docs/instructions/・docs/TODO.md・scripts/deploy_gate.py・scripts/dev_safety_notify.py・tests/test_deploy_gate.py・tests/test_dev_safety_notify.py）

通る

  • 読むことは全部
  • PR のマージ（マージボタン・gh pr merge・コネクタのマージ。自動マージも通りますが、直前の取り込みと pytest が飛ぶので使いません）
  • kodai/… への push と削除
  • PR の作成（Create PR ボタン）とコメント
  • アプリのコードとテスト（基盤を除く）
  • docs/SPEC.md・docs/KNOWLEDGE.md・requirements.txt

図4: 三田さんの殻の番人（guest_guard）の線。GitHub の Web 画面の操作は番人の外

三田さんの殻には、間違えやすい操作を止める番人（起動時に読み込まれる hook）が入っています。止めたときは理由と、docs/CONTRIBUTING.md のどの節を見ればよいかを出します。

番人は Claude の操作の字面を読む補助です。GitHub の Web 画面で main のファイルを直接編集するのは番人の外ですが、PR が記録にならないので使わないでください。基盤に触れた更新が main に入ると、その後のデプロイを 1 章の門が止め、拓也の見張りにも届きます。

6. PR のテストと赤い CI

PR のテストの証拠は、三田さんの殻で撃った python -m pytest -q -m "not integration" の出力です。PR 本文にそのまま貼ってください。PR の前に、文脈を持たないサブエージェントに diff だけを渡した自己レビューの所見も貼ります（PR テンプレートに欄があります）。

CI の pr-tests は、2026 年 12 月 1 日（火）9:00（日本時間）まで数秒で赤になります。拓也のアカウントの Actions の月の枠が切れているためで、コードの赤ではありません。三田さんの Claude はこの赤の通知で起こされることがありますが、直そうとしなくて大丈夫です。

本番に出る前には、Cloud Build のテストの段が同じ pytest を必ず撃ちます。赤ならデプロイされません。
