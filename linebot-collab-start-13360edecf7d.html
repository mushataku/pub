三田さんへ: line-bot の始め方

三田さんが line-bot に最初の PR を出すまでの 1 枚です。細かい決まりは repo の docs/CONTRIBUTING.md にあります（repo は private なので、招待を受けてから開けます）。

line-bot では、マージボタンを押さないでください。

押すと本番の入口で止まり、拓也のデプロイも一緒に止まります（理由は 1 章）。GitHub コネクタのマージ・自動マージも同じです。Approve は拓也がマージの合図に使うので、これも押さないでください。GitHub の Web 画面でファイルを編集して commit するのも、main の更新になるのでやめてください。

もし押してしまったら、自分で戻さず（revert も main の更新になります）、すぐ LINE の作業グループに書いてください。拓也が解除します。

1. なぜ押さないのか

  1. 三田さんの操作マージボタンを押すmain が三田さんの名前で更新される
  2. →
  3. 本番の入口（Cloud Build の最初の段＝門）門が止めるmain を更新したのが拓也でなければ本番に出さない
  4. →
  5. その結果拓也のデプロイも止まる拓也が解除するまで、次のデプロイも同じ門で止まる

図1: 三田さんが main を更新したときに起きること（赤＝止まる）

line-bot は main が更新されると、そのまま本番の LINE Bot にデプロイされます。ドライバーが配送中に使っているので、拓也が見ていない更新は本番の入口にある門（デプロイの最初の段の検査）で止めています。

門が見るのは「誰が main を更新したか」です。三田さんの PR を拓也がマージするのは拓也の更新なので通ります。三田さんがマージボタンを押すと三田さんの更新になります。門はそれが本番に出るまでの範囲に残る限り止め続けるので、拓也が解除するまで拓也の修正も出せません。

もう 1 つ、三田さんが作者のコミットが基盤のファイル（.claude/・.github/・cloudbuild.yaml・Dockerfile・CLAUDE.md など・5 章）に触れていると、拓也がマージしても門が止めます（docs/TODO.md と門の試験 2 本だけは門でなく番人が止めます）。基盤を触らない理由はこれです。

2. 全体の流れ

  1. 三田さん仕事を決める札が 実装OK の Issue か、小さな修正
  2. →
  3. 三田さんの Claude枝で実装・テストkodai/…
  4. →
  5. 三田さんPR を出すURL を作業グループに 1 行
  6. →
  7. 拓也ApproveGitHub で
  8. →
  9. 拓也の Claudeマージと見届け門・テスト・本番に載ったかを確かめる

図2: 青が三田さんの番、緑が拓也の番。三田さんは PR を出したら止まる

三田さんがやるのは PR を出すところまでです。拓也が Approve すると、拓也の Claude が Approve したコミットと PR の先頭が同じかを確かめてマージし、Cloud Build（門・テスト・デプロイ）と本番の /version で載ったことを見届けます。Approve の後に直して push したら先頭がずれてマージされないので、作業グループに「再 push した」と 1 行書いてください。

PR を出すと、拓也の claude.ai の自動レビューが所見のコメントを 1 件付けます。承認ではないので、気になる所見だけ直せば十分です。

枝が main から遅れて衝突したら、rebase は三田さんの Claude が自分の kodai/… の枝の上でやってください。

3. 最初の 1 本（殻の確認 PR）

最初の PR は、ドライバーに見えない「殻の確認」です。殻は claude.ai/code で line-bot を開いたときのセッションの環境のことで、三田さんの殻でも line-bot の仕組み（起動の案内と、間違えやすい操作を止める番人＝5 章）が働くかを測ります。この PR は拓也が読んで閉じます（マージしません）。

  1. 招待を受けて line-bot を開くGitHub の招待を受けたら、claude.ai/code で mushataku/line-bot を開きます。repo の一覧に出てこなければ、作業グループに書いてください（拓也側の設定で直します）。
  2. 環境変数を足す 任意claude.ai の環境設定に LINEBOT_GUEST=1 を足すと、起動時の待ち 20 秒が消えます。起動時に「拓也の殻か三田さんの殻か」を見分けるため最長 20 秒待っていて、足すと三田さんの殻だとすぐ決まります。足しても害はなく、足さなくても約 41 秒で動きます。
  3. Claude に頼む「docs/CONTRIBUTING.md の §2 にある殻の確認の 6 項を測って、kodai/0-shell-check から PR を出して」と頼みます。Claude は最初に切られた claude/… の枝から git switch -c kodai/0-shell-check で切り直します。止まるはずの操作は全部 --dry-run か取り消せる形で撃ち、本物の main への push はしません。止まらなかった操作で変わったものは push せずに捨てます（捨て方は docs/CONTRIBUTING.md §2 の項目 3）。PR は Create PR ボタンで出します（claude.ai/code の GitHub の通り道が gh pr create の GraphQL を通さないことがあります）。ボタンが出ない・claude/… の枝から出そうになるときは、Claude に REST（POST …/pulls）で kodai/0-shell-check から出させます。
  4. PR に表を貼る差分は結果の表を書いた 1 ファイル（docs/shell-check/kodai.md）だけです。PR 本文にも同じ表（項目・期待・実測・コマンドと出力の要点）を貼り、PR テンプレートの残りの欄も埋め、テストの欄には撃った pytest の出力を貼ります（本文は Claude に REST の PATCH …/pulls/<番号> で書かせても、Web 画面の PR 本文の編集で直してもかまいません。本文の編集は main を変えません）。止まった操作は止まった文言を、止まらなかった操作はそのまま書けば正解です。
  5. 作業グループに URL を 1 行いつも拓也と依頼をやり取りしている LINE の作業グループに PR の URL を貼って、拓也が閉じるのを待ちます。
  6. 次の 1 本拓也が殻の確認 PR を閉じたら、Issue #6 に進みます。LINE の送信や AI の月の上限に当たったとき、いまは黙って失敗しているので、それを知らせる仕組みとドライバーへの一言を足す仕事です（札 実装OK）。

4. 枝（branch）と Issue の札（label）

使う枝

  • kodai/<番号>-<話題>
  • 例: kodai/6-limit-alert（番号は Issue の番号。Issue が無い小さな修正は 0）

使わない枝

  • main
  • claude/…（誰が作ったものでも拓也の機械が毎時片付ける。claude.ai/code が最初に切る枝もこれなので切り直す）

図3: 三田さんの枝は kodai/ で始まるものだけ

Issue の札は 2 つです。設計判断待ち は拓也の答え待ちで、まだ実装しません。実装OK が付いたら実装してよい合図です。

ドライバーの操作が変わる・新しい外部サービスやお金が要る・優先順位が絡む、のどれかに触れるなら Issue で拓也に聞いてください。触れない小さな修正は Issue なしで PR から直接で構いません。

5. 番人が止める操作

番人が止める（Claude の操作）

  • main への push・Claude からのマージ
  • kodai/ 以外の枝への push と削除
  • [skip ci] などの印つきの commit
  • コネクタのマージ・自動マージ・Approve
  • 基盤のファイルの編集（.claude/・.github/・cloudbuild.yaml・Dockerfile・CLAUDE.md・docs/instructions/・docs/TODO.md・門の script など）

通る

  • 読むことは全部
  • kodai/… への push と削除
  • PR の作成（Create PR ボタン）とコメント
  • アプリのコードとテスト（基盤を除く）
  • docs/SPEC.md・docs/KNOWLEDGE.md・requirements.txt

図4: 三田さんの殻の番人（guest_guard）の線。GitHub の Web 画面の操作は番人の外

三田さんの殻には、間違えやすい操作を止める番人（起動時に読み込まれる hook）が入っています。止めたときは理由と、docs/CONTRIBUTING.md のどの節を見ればよいかを出します。

番人は Claude の操作の字面を読む補助です。GitHub の Web 画面での直接の編集やマージボタンは番人の外なので、使わないでください。使うと 1 章の門が止め、拓也のデプロイも一緒に止まります。

6. PR のテストと赤い CI

PR のテストの証拠は、三田さんの殻で撃った python -m pytest -q -m "not integration" の出力です。PR 本文にそのまま貼ってください。PR の前に、文脈を持たないサブエージェントに diff だけを渡した自己レビューの所見も貼ります（PR テンプレートに欄があります）。

CI の pr-tests は、2026 年 12 月 1 日（火）9:00（日本時間）まで数秒で赤になります。拓也のアカウントの Actions の月の枠が切れているためで、コードの赤ではありません。三田さんの Claude はこの赤の通知で起こされることがありますが、直そうとしなくて大丈夫です。

本番に出る前には、Cloud Build のテストの段が同じ pytest を必ず撃ちます。赤ならデプロイされません。
