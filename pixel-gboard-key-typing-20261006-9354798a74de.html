Pixel の Gboard の鍵を1つずつ押して打つと、ページからどう見えるか

自陣の localhost ページを Pixel 7a の Chrome で開いて測定（実サイトには触っていない）。各図の棒＝平均・黒線＝±SE。

結論（2026-10-06 実測・Pixel 7a・Gboard）
  1. 鍵の位置は機械で決まる（26/26）。この Pixel の Gboard は QWERTY ではなく日本語 12 キーで、英字も 12 キーの多タップ（ABC/DEF…）。10/4 に「13 文字中 4 文字」しか拾えなかったのは、かなの鍵盤の上で英字1字の鍵を探していたため。「あa1」の鍵で英字モードにすると、(a) dump の node・(b) 鍵盤の窓の矩形×格子・(c) スクショの白い鍵、の3つとも 26 字すべてで (a) の鍵の矩形とタップ回数に一致した。
  2. Gboard は adb tap の押下を普通の押下として受ける。鍵の押下だけで pixelfidelitytestabc を 4 本打ち、4/4 一致（20 字に 47 回押す＝多タップ＋同じ鍵の連続の間に →）。
  3. ページから見た違い: K4（Gboard 経由）は keydown が keyCode 229・inputType は insertCompositionText・composition 事象あり（Android で人が Gboard で打つときの見え方）。K1（CDP keyboard.type）は実字の keyCode・insertText・composition なし・字間隔 134±1ms（指定の delay どおり一定）。Android の Chrome で「実字の keyCode が出て composition が無い」こと自体が、人の画面キーボードと違う見え方。
  4. K4 は遅い: 端末側で 1 字 366±38ms（1 本 約 15 秒）。adb shell input tap を 1 回ずつ起こす分と、12 キーの多タップの分がある＝「人の速さ」にするのは次の票（cont2）。
  5. [未到達] K2（adb input text）・日本語（かな 12 キー→変換→確定）・QWERTY（Gboard の設定「英字入力は QWERTY」）: 1 回目はページの記録が 3 本目から落ち（下の罠）、撃ち直しは端末の鍵（あんスタの長回し）が 30 分空かず打ち切り。撃つ前後で IME・subtype・Gboard のモード（かな）・「英字入力は QWERTY」＝off は同じ（下の表）。
罠: ページの記録を fetch(..., {keepalive:true}) で送ると、Chrome は keepalive の body を 1 ページの累計 64KB で打ち切る。K4 の 1 本は約 31KB＝3 本目から以後の記録が全部落ちた（端末の入力欄には正しく入っていた）。keepalive を外した。

問1 Gboard の鍵の位置を機械で決められるか

問1 位置決めの手ごとの、dump と一致した字の数（12key）

英字モードの鍵盤（12key）で、各手が決めた点が dump の鍵の矩形に入り、タップ回数も同じ字を数えた。(a) は基準そのもの＝拾えた字の数。欠け: (a) dump の node なし・(b) 窓の矩形×格子 なし・(c) スクショの白い鍵 なし

問2 鍵を押して打った文字は、K1/K2 と何が違うか

問2 字間隔（ページが見た keydown→keydown）

K4 は鍵を押すたび（多タップの2回目・3回目、→ も）に keydown が出る＝字の間隔ではなく押下の間隔。adb input tap は1回ごとに端末で input を起こすので数百 ms かかる。K1 は delay=120ms の指定どおり揃う。

問2 入力欄の最終値が打った文字列と一致した割合

KJ は「てすと」か「テスト」で一致。SE は √(p(1-p)/n)（n は各腕の本数）。
