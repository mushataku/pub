結論: 今の規模（1件ずつ・数分おき）なら home で撃てばよい。どの経路でもサイト側の遮断は0回で、android・tether が落ちたのは経路のせいではなく道具の未熟さ（入力が遅い・絵の読み違い・待ち切れ）だった。

  • 撃つ間隔は効いていない（下の⑥）。一番強い証拠は IP も Chrome も固定の home: 同じ Chrome の直前から 52秒・3分・3分・3分の間隔で4回とも届いた。切断の仮印（30分の冷却）は1回も立たなかった＝前の子が見た「約1.3分おき17回の連打で切られる」型は、この回数では出ていない。android と tether は毎回 IP が変わるので、IP 単位の連打の検証にはならない。
  • android は遅く、そのままでは本番に使えない。所要は届いた3回で 453〜545 秒（home は 57〜67 秒、初回だけ 357 秒）。時刻つきログのある回では、タブを借りてからアイテム認証まで 2分42秒、認証から確認画面まで 4分41秒（n=1）。fc-sui の1回はお客様情報の入力中に待ちが切れた。さらに Pixel の Chrome は新しいタブを開けず既存タブを借りて歩く＝顧客ごとに Cookie を分けられない（ログに毎回警告。dry-run だけ許している）。

次の一手: ①home の同じ IP で何件まで続けて撃てるかを測る（経路を増やす要否はここで決まる） ②android の入力が遅い理由を区間ごとに切り分け、顧客ごとに Cookie を分ける手を作る（どちらも本番で使う前提） ③所要秒の内訳（経路の準備・入口・認証・入力）を試行台帳に残す。

① 確認画面まで歩けた率

入口→希望→アイテム認証→申込者情報→確認画面の全部を通った割合。経路が変えうるのは「歩けるか」（Akamai の遮断・認証の追加・エラー）。

② アイテム認証を1回目で通せた率

認証の画面まで着いた試行のうち、1回目の答えで進めた割合（分母は認証に着いた数）。経路で問題の出方が変わるかを見る。

③ 遮断・エラーになった率

アイテム認証の壁・入口に届かない・タイムアウト等、途中で止まった割合。高い腕は撃つと落ちる。

④ 所要秒（平均±SE）

1回の撃ちに掛かった秒（機内モードの往復・DataProxy の起こし直し・アイテム認証の撃ち直しを含む）。届かなかった回も入る。遅い腕は連続で撃つ間隔に効く。中央値は上の表。
